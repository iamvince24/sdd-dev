# SDD 需求

這份規劃定義 sdd-dev 的需求確認、計畫、開發與驗收流程。需求、限制與驗收條件必須清楚；實作者在約束內決定實作方法，並以可檢查的證據確認結果。

### 初始化

1. 設定 Spec 來源 path 與版本識別方式。來源沒有版本號時，使用內容雜湊識別，不強制來源採用新的版本規則。
2. 確認哪些專案資料夾需要使用 sdd-dev，記錄 workspace path、主要技術與專案既有規範。
3. 確認各 workspace 的驗證能力，記錄可執行的指令、執行條件與已知限制，包括 lint、型別檢查、unit test、integration test、E2E 與 build。
4. 沒有既有自動化測試時，仍須依本次需求安排 runtime smoke test、瀏覽器操作、API 請求或人工驗收等適當方法。無法驗證的項目須記錄原因，不得視為通過。
5. 確認各 workspace 的版本號規則，並由使用者選擇 sdd-dev 的安裝模式及專案內資料是否納入版控。
6. 初始化結果可以重用；技術設定、依賴、驗證指令或相關專案規範改變時，更新受影響部分，不必每個任務重新掃描完整專案。Git 狀態、既有修改與當次權限須在每次開始或恢復 run 時重新確認，不直接沿用舊紀錄。

### 執行環境與權限邊界

1. 每次開始或恢復 run，確認各 workspace 的 branch、HEAD SHA、未提交修改與相關未追蹤檔案，建立本次執行基準；非 Git 專案使用快照識別。恢復時若基準改變，先檢查受影響的任務、核准與證據。
2. 區分執行前已存在的修改與本次成果，不自行覆寫、丟棄或納入本次 commit。修改範圍重疊時，先判斷能否保留既有成果並繼續；無法安全分離或需要決策時，只暫停受影響範圍。
3. 記錄本次允許寫入的位置，以及 shell、網路、依賴安裝、環境變數、外部服務、資料庫與正式環境的操作限制。此邊界適用於所有角色與階段，包括探索實驗、安裝依賴、執行測試及重跑驗證。Workspace 驗證能力中已宣告的驗證輸出（例如 build 或 coverage 產物）屬允許寫入範圍；安裝依賴、變更 lockfile、使用網路與存取外部服務須有對應授權紀錄。
4. 已授權範圍內可自主操作；超出範圍的破壞性操作、共享歷史重寫或外部資料變更，須取得對應授權。例如 `git reset --hard`、force push、刪除範圍外檔案與正式資料庫寫入，不能由一般實作授權推定。授權以操作類別與適用範圍記錄，並引用使用者的決策，只在該次 run 有效；已明確授權的同一操作範圍不重複詢問，仍須遵守執行平台的限制。
5. Context、日誌、工具輸出與驗證證據不得保存秘密值；必要資訊以遮蔽或引用方式記錄。權限紀錄只描述可使用的能力及用途，不抄錄憑證內容。
6. 區分由執行平台強制限制的邊界與僅由流程約定的邊界，不把 prompt 規則視為已具備隔離能力。強制點分三層：經由 sdd-dev 工具的操作由工具檢查；agent 直接執行的指令由平台 hook 等機制攔截；兩者皆無法提供時屬流程約定，須記錄為能力缺口。平台無法提供本次必要限制時，回報替代方式與能力缺口；仍無法滿足時，受影響工作維持受阻。
7. 本節處理 agent 的操作安全；D7 持續檢查產品程式碼的安全風險，兩者各自適用，不新增審查維度或核准關卡。

### 確認需求

#### 需求來源與現況查核

1. 有 Spec 或相關文件（例如後端 API 文件）時，指定位置或貼上內容；沒有文件時，由使用者提供需求。
2. 對照需求與 codebase，區分以下資訊，並記錄相關文件或程式碼位置：

   | 類型 | 定義 |
   | --- | --- |
   | Current State | 目前實際行為與既有設計 |
   | Target State | 本次需求希望達到的狀態 |
   | Expected Delta | 本次本來就要修改的差異，不視為衝突 |
   | Conflict | 需求與必須維持的既有約定或限制無法同時成立 |
   | Unknown | 現有資訊不足以判斷的事項 |
   | Assumption | 不改變需求、可回復且符合既有慣例的暫定選擇 |

3. 先透過文件、codebase 或小型可回復的實驗解決未知事項。若仍無法判斷，且會影響需求範圍、產品行為、對外介面、資料語意、安全邊界或不可逆操作，才請使用者決定。
4. 其餘可回復、符合既有慣例的選擇，記錄假設與依據後繼續；假設若被推翻，重新檢查受影響的需求與任務。
5. 需要決策時，產生確認報告，列出問題、影響、可行選項與建議。使用者回答後更新同一份報告的 revision，再查核受影響部分；不重複詢問已解決的問題。
6. 阻塞只暫停受影響的工作及其依賴項目，其餘已獲授權的獨立工作可繼續。

#### Execution Spec 與驗收條件

1. 需求釐清後產生 `Execution Spec`，作為本次執行的需求基準，與原始 Spec 區別。`direct` 可用包含適用必要內容的簡短紀錄呈現，不強制另建完整文件；`selected_advisors` 僅整理諮詢範圍與結論，不因此建立實作授權。
2. Execution Spec 包含來源引用與版本、已確認的澄清、範圍與排除範圍、限制、整合介面、假設及驗收條件。不得自行改變原始需求；差異須能追溯到使用者同意的決策。
3. 每個需求與驗收條件有穩定的識別碼，建立「需求 → 驗收條件 → 任務 → 驗證證據」的對應。新功能與新頁面也必須建立此對應。
4. 驗收條件在實作計畫前定義，以 Given（條件）、When（動作）、Then（結果）描述可觀察行為，涵蓋需求相關的正常、錯誤與邊界情況。計畫階段再補上具體驗證方法。

   | 欄位 | 內容 |
   | --- | --- |
   | 需求／驗收 ID | 對應來源需求與驗收項目 |
   | Given／When／Then | 前置條件、操作與預期結果 |
   | 驗證方式 | 測試、瀏覽器、API 或人工操作等方法 |
   | 通過條件 | 明確、可觀察的判定標準 |
   | 證據與結果 | 執行後填入實際結果、證據位置及對應程式碼版本 |

5. `full_pipeline` 必須取得使用者對 Execution Spec 的同意，才能進入實作計畫。核准須對應文件 revision。
6. 本次執行以對應路線的 Execution Spec 為需求基準；`full_pipeline` 或使用者指定需核准時，必須使用已核准 revision。`direct` 不額外強制獨立的 Spec 核准步驟，但仍受使用者需求與授權範圍約束。任何路線對原始 Spec 的差異，僅在具有使用者明確同意的決策紀錄時有效；發現未獲同意的差異時，暫停受影響項目並釐清，不自行選擇其中一份。
7. 原始需求或已核准決策改變時，先完成影響評估，再更新 Execution Spec 並納入本次執行；重新檢查受影響的計畫與驗收條件。會改變範圍、行為或重要限制的修訂，必須重新取得同意；未受影響的核准不必重做。沿用既有核准時，須附逐段列出修訂差異的影響評估；差異涉及範圍、排除範圍、限制、整合介面、需求或驗收條件時不得沿用。沿用紀錄須列入報告，使用者可推翻並改為重新核准。

### 實作計畫

#### 計畫範圍

1. 計畫必須定義目標、範圍、限制、必要架構決策、整合介面、預期修改範圍、任務依賴與驗證方式。
2. 實作者可在這些約束內決定實作方法。涉及對外介面、資料遷移、安全邊界或高成本決策時，須在實作前確認必要細節；不預先指定沒有必要的逐行修改方法。
3. 優先沿用 codebase 的既有模式與資源。每個需求都必須對應任務與驗收條件；超出已同意範圍的工作不得自行加入。

#### 計畫審查

1. 完整流程由不同於 planner、使用獨立上下文的 reviewer 審查。Reviewer 必須能取得 Execution Spec、計畫、專案限制與相關 codebase 證據；不得只依 planner 的摘要判斷。
2. 保留 D1～D7 作為檢查面向。分數若有提供，只供診斷，不以平均分數或 B 等級作為通過門檻。

   | 維度 | 主要檢查內容 |
   | --- | --- |
   | D1 Ambiguity 明確性 | 需求、驗收條件、scope 與名詞是否明確一致 |
   | D2 Gaps 完整性 | 錯誤處理、邊界情況、migration、rollback、驗證、型別／介面與依賴是否遺漏 |
   | D3 Contradictions 矛盾 | 步驟、資料結構、命名與任務輸入輸出是否互相矛盾 |
   | D4 Conflicts 衝突 | 是否破壞必要既有功能、違反專案慣例、技術版本限制或與其他工作衝突 |
   | D5 Architecture 架構 | 是否過度設計或設計不足、責任混雜、耦合過高，是否有更簡單做法 |
   | D6 Maintainability 維護性 | 複雜度、hardcode、任務與 commit 邊界、可測試性與技術債 |
   | D7 Security 安全性 | Auth、權限、輸入驗證、XSS／CSRF／SSRF／SQL Injection、機密資料與檔案處理等適用風險 |

3. 不適用的維度須附理由。適用時，重大安全問題、資料遺失風險、必要 migration 缺漏與對外介面不相容，必須列為阻塞問題，不得由其他分數抵銷。
4. 每個問題列出位置、依據、嚴重程度、建議與解除條件，並區分阻塞問題與非阻塞建議。

   | 結果 | 判定條件 | 下一步 |
   | --- | --- | --- |
   | READY | 沒有尚未解決的阻塞問題 | 進入使用者核准階段，不代表已授權實作 |
   | REVISE | 存在 agent 可自行修正的阻塞問題 | Planner 修改後，交由獨立 reviewer 重審 |
   | BLOCKED | 缺少必要決策、資訊或能力 | 暫停受影響範圍，列出解除條件與可行選項 |

5. 自動修訂預設最多兩輪，可由使用者調整；一輪指一次修改及其後的獨立重審。到上限仍未通過時，停止自動重送，回報剩餘問題與選項，不自行縮小已同意的需求。這是初始流程設定，不是已驗證適用所有任務的固定門檻。

#### 任務、commit 與平行工作

1. 依共同目的、依賴關係與可驗證性拆分任務及 commit。每個 commit 應有清楚用途，並維持當下應成立的功能與必要檢查。Agent 預設不建立 commit；只有使用者在 Plan 核准時明確允許依任務邊界 commit，agent 才能 commit，且不 push。未允許時，由使用者依建議的 commit 邊界自行處理。
2. 任務沒有未解決依賴，且檔案修改範圍、共享狀態與介面責任可分離時，才使用多個 subagent 平行開發；同時遵守本次的委派限制。
3. 指定各任務的修改責任範圍與整合負責者。會同時修改相同檔案或緊密耦合介面時，須先拆開責任或改為循序工作；依序 commit 不能取代這項安排。
4. 有依賴的任務須等前置成果通過相關驗證後，才能依賴該成果繼續。整合後重新執行受影響的檢查。

#### 驗證計畫與核准

1. 為每個驗收條件選擇能證明該行為的方法，優先使用既有工具；必要時依風險補上針對性的測試或操作驗證，不要求為每個小改動建立完整測試框架。
2. Lint、型別檢查、build、測試與實際操作各自證明不同事情。Build 成功不能代替功能驗收；單純 diff review 也不能證明執行時行為正確。
3. 分別列出每個任務／commit 的必要檢查、整合檢查與最終驗收。驗證能力不足時，安排能證明同一條件的替代方法；仍不足則標示受阻，不能降低通過標準。
4. `full_pipeline` 的計畫通過審查後，仍須取得使用者對該 revision 的同意，才能進入開發。影響需求、介面、風險或重要設計的變更須更新計畫，重做受影響的審查與核准；約束內的實作選擇不必逐次提問。

### 開發與驗證

#### 問題處理

1. 遇到問題時記錄在 Markdown 問題清單，包含影響範圍、處理方式、理由與目前結果。
2. 影響後續正確性、需求約定、安全、架構或整合的問題，須在依賴它的工作繼續前處理。Agent 能在該路線已獲授權的範圍內解決時直接修正，不因問題嚴重就一律要求使用者決策。
3. 非必要整理與無關技術債可以延後，須記錄影響及延後理由，不將延後處理設為預設。
4. 需要改變需求或缺少必要決策、資訊、能力時，依確認需求的規則提問，並標示受影響工作為 blocked。
5. 修正預設以新增 commit 呈現，不修改既有 commit；是否由 agent 建立 commit 依任務 commit 的授權規則。未取得明確授權，不重寫已分享的 Git 歷史；只有問題紀錄或程式碼 TODO 不算解除阻塞。

#### 分段驗證與最終驗收

| 時點 | 必須滿足的條件 |
| --- | --- |
| 每個任務／commit | 本次變更的必要檢查，以及當下應維持的回歸檢查通過 |
| 多項成果整合後 | 受影響的介面、整合與回歸檢查通過 |
| 全部實作完成 | 所有必要驗收項目與整合檢查通過 |
| 最終回報前 | 證據對應目前成果；完整流程另完成獨立結果審查 |

1. 每個驗收項目記錄「通過、失敗、未執行、受阻」及證據。人工驗收尚未完成時，不得填為通過。
2. 已知的既有檢查失敗須記錄基準、與本次變更的關係及影響；不自動視為本次阻塞，也不視為通過。須有對應執行前程式碼版本的基準證據確認失敗原已存在（手動記錄的已知失敗只能作為提示，不能當作基準證據），並說明本次未使其惡化、且不影響本次必要驗收，才能列為非阻塞的既有問題。無法確認關聯，或因此無法證明必要驗收條件時，受影響項目維持受阻；不能默默忽略，也不能把沒有執行的檢查寫成成功。
3. 完整流程的獨立 verifier 根據 Execution Spec、實際變更及證據判定成果，必要時重跑關鍵操作，不只接受 executor 的完成摘要。
4. 證據須綁定程式碼版本及相關執行條件；成果改變後，重新驗證受影響部分，不能沿用已失效的通過結果。
5. 必要驗收失敗、未執行或受阻，或完整流程所需的獨立審查尚未完成時，不得宣告整體完成。可回報已完成範圍、剩餘限制與解除條件。
6. 最終報告列出需求完成情況、驗證證據、剩餘問題及延後事項。中間 commit 不必提前通過尚未完成之後續功能的驗收。

### 共同需求

#### 開源、跨工具與模型角色

1. sdd-dev 要成為可供他人使用的開源專案，以 MIT License 發布，並在發布 repo 根目錄提供 `LICENSE`。支援 Claude Code、Codex 與 Cursor 使用者；這是支援目標，各平台能力須實際確認，不能假設完全相同。
2. 流程使用 scout、planner、plan-reviewer、executor、security-reviewer、verifier 等角色描述責任；角色是能力分工，不代表每個任務都必須建立所有 agent。
3. 模型選擇由獨立設定對應角色，依任務難度、推理、實作與驗證能力分配，不把模型名稱寫死在流程中，避免強模型處理不需要它的簡單工作。
4. 保留 [Pilotfish](https://github.com/Nanako0129/pilotfish) 作為模型設定的待查核參考；採用具體設計前確認其內容與本專案需求，不把外部專案描述直接當成實作承諾。
5. 平台缺少獨立上下文、委派、瀏覽器或必要驗證能力時，回報替代方式與限制。替代方式仍須符合原本的必要條件；無法滿足時保留受阻狀態，不假裝具備該能力。

#### 安裝位置與版控

1. 提供兩種安裝模式：`repo-local` 把 sdd-dev 安裝在目標 repo 的 `.sdd-dev/tool/`；`shared-sibling` 把一份 sdd-dev 安裝在多個 repo 的同層資料夾，由多個 repo 共用。共享安裝須明確記錄各 repo 的路徑對應，不把某個 repo 的設定或執行產物混入共享安裝。
2. 不論安裝模式，各 repo 的設定與執行產物都放在該 repo 的 `.sdd-dev/`。初步目錄分工如下；實作時可依平台能力調整名稱，但須維持工具、設定與每次 run 的邊界：

   | 路徑 | 內容 |
   | --- | --- |
   | `.sdd-dev/tool/` | `repo-local` 模式的工具檔；`shared-sibling` 模式不使用 |
   | `.sdd-dev/config/` | 此 repo 的 workspace 對應、模型角色及流程設定 |
   | `.sdd-dev/runs/<run_id>/` | Execution Spec、Plan、報告、日誌與驗證證據等該次執行產物 |

3. 初始化時讓使用者決定 `.sdd-dev/` 是否納入目標 repo 版控，並記錄選擇。選擇排除時，建立或指示使用者設定適用的 Git 忽略規則；檢查目錄內是否已有被追蹤的檔案，以及忽略規則是否生效。已追蹤的檔案不能只靠忽略規則排除，須回報並由使用者決定如何處理，不自行改動既有追蹤狀態。非 Git 專案只記錄保存位置，不宣稱具備 Git 隔離。
4. 選擇納入版控時，明確顯示將被追蹤的範圍；秘密值不得寫入設定、日誌或產物。不同 repo 可各自選擇版控方式，共享安裝的工具檔不屬於任一目標 repo 的版控選擇。
5. 安裝後不主動更新 sdd-dev；只在使用者要求時更新。更新前顯示目前與目標版本、受影響的 repo 與設定，保留既有 run 產物，並檢查是否需要遷移。搬移 repo 或切換安裝模式時，重新檢查路徑對應與版控狀態；解除安裝不得默默刪除設定或 run 產物。

#### 角色上下文與產物提供方式

1. 依角色與當前任務提供相關內容，不預設將完整流程文件、所有產物與工作對話交給每個 agent。所有角色均須取得適用的專案規範、操作邊界與使用者限制；以下定義各角色的預設輸入，不要求每次建立所有角色。

   | 角色 | 預設提供的內容 |
   | --- | --- |
   | scout | 需求來源、探索問題、workspace 與相關現況資料 |
   | planner | Execution Spec、現況證據、專案限制、整合介面與驗證能力 |
   | plan-reviewer | Execution Spec、Plan、適用檢查面向，以及可直接查閱的 codebase 證據 |
   | executor | 本次任務、相關 Spec／Plan 段落、驗收 ID、修改責任範圍、依賴與驗證方式 |
   | security-reviewer | 相關需求、設計或變更、資料流、安全邊界與證據 |
   | verifier | 驗收條件、待查核的完成宣稱、實際 diff、程式碼版本、證據與執行條件 |

2. 預設提供精簡內容，但允許角色在權限內追查必要的原始資料。精簡不得省略會影響任務的需求、限制、跨任務介面或驗收條件，也不能只提供前一角色的摘要而無法查閱來源。
3. 提供的內容須附適用的來源 revision、需求／任務 ID 與 codebase_ref，保留「需求 → 驗收條件 → 任務 → 證據」對應。來源改變時，更新受影響的角色輸入，並依既有規則重查相關核准、審查與驗證結果。
4. 獨立 reviewer／verifier 不承接 planner／executor 的完整工作對話；可讀取其完成宣稱與正式報告作為待查核資訊，但須根據需求、實際成果與原始證據自行判斷。
5. 角色上下文的精簡不改變既有授權、委派限制或獨立審查條件。平台缺少必要能力時，依跨工具能力限制的規則處理。

#### 文件保存與追溯

1. 流程產物保存在各使用者專案的 `.sdd-dev/runs/<run_id>/`，版控方式依「安裝位置與版控」的使用者選擇。支援依 run_id 恢復執行與匯出；程式碼及必要測試仍依專案慣例納入版控。
2. Execution Spec、Plan 及用於核准或審查的正式報告，保留 revision 與簡短變更摘要，不要求採用語意化版本號。執行日誌、工具輸出與驗證證據以 run_id、時間及對應程式碼版本保存，不逐份維護 changelog；已被核准或審查引用的內容不得直接覆寫。

   | 識別資訊 | 用途 |
   | --- | --- |
   | run_id | 識別一次執行及其產物 |
   | source_spec_version 或內容雜湊 | 識別需求來源；多份來源分別記錄 |
   | artifact_revision | 識別 Execution Spec、Plan 及用於核准或審查的正式報告修訂 |
   | codebase_ref | 識別各 workspace 的 Git SHA；有未提交修改時，另記錄相關差異或快照識別；非 Git 專案使用快照識別 |

3. 核准、審查結果與驗證證據都要對應相關 revision 或程式碼版本。恢復執行時先確認來源與程式碼是否改變，再重查受影響部分。
4. 給使用者閱讀的文件先採 Markdown，依決策範圍分段，讓使用者一次專注一個範圍；避免把完整執行紀錄塞進決策報告。

#### 流程量測與評估

1. 每次 run 保留最小量測紀錄，沿用 run_id 與既有產物，不新增每階段的人工報告或核准關卡。目的在於判斷選路、審查與核准是否改善結果，以及付出的時間與互動成本。

   | 類別 | v1 紀錄內容 |
   | --- | --- |
   | 執行識別 | run_id、流程／選路政策版本、平台與模型設定 |
   | 選路 | 初始路線、最後路線、升級原因、主要風險特徵 |
   | 流程成本 | 澄清、計畫修訂、阻塞、subagent 與人工核准次數；執行時間與等待時間分開記錄 |
   | 驗證 | 必要驗收首次執行結果、最終結果，以及未執行與受阻項目 |
   | 人工決策 | 核准是否帶來需求、設計或風險決策的變更，以及使用者覆寫流程建議的次數與原因 |
   | 後續結果 | 是否完成，以及已觀察到的返工、重新開啟或回復變更，附觀察時間與依據 |

2. 計數以實際事件為準：一次要求使用者回覆的澄清算一次；計畫修訂輪次沿用計畫審查的定義；阻塞按受影響項目進入受阻狀態的事件記錄，重複回報不重複計數；subagent 計實際建立數；核准計使用者實際核准決策，與核准請求分開。無法取得的量測值記為未知，不填為零。
3. `first_pass_success` 指對應需求 revision 的所有必要驗收在各自首次執行時即通過；仍有未執行或受阻項目時，不得標為成功。`final_pass_success` 依目前成果的必要驗收及有效證據判定，不能用 build 成功代替。兩者均不能取代路線要求的獨立審查或整體完成條件；需求 revision 改變時保留原紀錄，不用重設基準掩蓋失敗。
4. 沒有追蹤到後續結果時，記為未知，不能視為沒有返工。比較流程版本或路線時，需一併考慮任務風險、平台、模型與觀察範圍，不直接以不同任務群的成功率推論某條規則有效或無效。
5. 保留少量可重跑案例，涵蓋局部修改、介面變更、既有檢查失敗與權限受限等情境；為案例記錄起始狀態、預期流程行為與驗收方式，供流程修改前後比較。先建立簡單案例與紀錄，不要求 v1 建置完整評測平台。
6. 指標預設本機保存，遵守產物保存與敏感資訊規則；啟用量測不代表授權向外傳送資料。依真實任務與可重跑案例的結果提出流程調整，不因累積到固定執行次數就自動取消核准或審查。

#### 路線、狀態與控制

自動選路前，先檢查需求是否明確、影響範圍、可回復性、對外介面、資料遷移、安全邊界與驗證能力。使用者明確指定的路線與限制優先；自動選路不得擴張實作授權。以下是初始選路政策，後續依實際使用結果調整，並記錄每次選擇理由：

| 路線 | 適用情況 |
| --- | --- |
| direct | 需求明確、影響局部且可回復，具備足以驗證本次變更的方法，且沒有尚未解決的重要不確定性；保留範圍、驗收與必要驗證的簡短紀錄，不強制產生完整流程的所有文件 |
| selected_advisors | 只需要諮詢而未授權實作時，找特定顧問釐清需求、架構或安全問題；結果回到目前工作，必要時升級 full_pipeline，但不得自行進入實作 |
| full_pipeline | 涉及重要介面變更、資料遷移、安全邊界、多個緊密相依模組、影響範圍大、難以回復或回復成本高、驗證能力不足以支撐變更風險，或探索後仍存在會影響需求、設計或驗收的重要不確定性時，預設選此路線。流程：需求確認 → Execution Spec 核准 → 計畫與獨立審查 → 計畫核准 → 開發與分段驗證 → 最終驗收與獨立結果審查 |

影響範圍依可能波及的功能、共用介面、資料與使用者判斷，不單以修改檔案數決定。升級 `full_pipeline` 不代表已解除未知事項、驗證能力或授權上的阻塞；受影響工作仍須取得必要決策、補足能力或維持受阻。

`blocked` 是可發生在任何路線、階段或任務的狀態，不是第四種路線。它表示缺少必要決策、資訊、能力或檢查結果，須記錄受影響範圍及解除條件；解除後回到原路線。

| 控制方式 | 意義 |
| --- | --- |
| fast-lane | 既定路線的精簡模式，不是獨立路線；可精簡文件篇幅、合併重複紀錄，並省略未被路線、風險處理或使用者要求的額外顧問。不得取消該路線所需的核准、獨立審查、追溯資訊與必要驗證 |
| cross-check | 完成後要求另一個唯讀 reviewer 檢查實際成果與證據 |
| ag／agentflow | 選擇 full_pipeline 的指令別名 |
| no delegation | 不委派給其他 agent，包括 worker 與 reviewer |
| plan-only／「先做計畫，等我確認」 | 完成需求與計畫階段（需要計畫審查的路線於審查通過）後停下等待使用者確認，不進入實作；使用者核准計畫後即可繼續 |

各實作路線的文件與必要條件如下；`selected_advisors` 維持諮詢用途，不納入此表。`direct + fast-lane` 沿用 direct 的必要條件，fast-lane 不額外降低門檻。

| 項目 | direct | full_pipeline + fast-lane | full_pipeline |
| --- | --- | --- | --- |
| 需求與現況查核紀錄 | 簡短，保留決策依據 | 精簡，保留必要依據與來源 | 必須 |
| 需求與驗收基準 | 簡短 Execution Spec 紀錄 | 精簡 Execution Spec，保留必要內容 | 完整 Execution Spec |
| Spec 使用者核准 | 依使用者明確要求 | 必須 | 必須 |
| Plan | 簡短任務與驗證安排 | 精簡，保留必要決策、依賴與驗證方式 | 必須 |
| 獨立計畫審查 | 依適用風險處理或使用者要求 | 必須 | 必須 |
| Plan 使用者核准 | 依使用者明確要求 | 必須 | 必須 |
| 需求 → 驗收 → 任務 → 證據對應 | 必須，可合併記錄 | 必須，可合併記錄 | 必須 |
| 必要驗證與證據 | 必須 | 必須 | 必須 |
| 獨立結果審查 | 依適用風險處理或使用者要求；cross-check 必須 | 必須 | 必須 |
| 最終回報 | 簡短，保留結果、證據與限制 | 精簡，保留結果、證據與限制 | 必須 |

組合規則：

1. 使用者明確設定的核准邊界與委派限制優先，不能因自動選路或 fast-lane 被略過。Direct 不自動繼承完整流程的兩次核准，但仍遵守使用者指定的停止點。
2. `full_pipeline + fast-lane` 僅依上述定義精簡文件、合併重複紀錄與省略額外顧問；Spec 與 Plan 仍須分別對應 revision 完成核准，不能取消完整流程所需的獨立審查及必要驗證。
3. `no delegation + cross-check` 有衝突：先完成可獨立進行且已授權的部分，保留待審狀態，說明可交由人工審查或由使用者調整委派限制，不能偷偷啟動另一個 agent。
4. `no delegation + full_pipeline` 保留完整流程的獨立審查條件，由人工或後續獲授權的獨立 reviewer 完成；審查紀錄須標明審查者類型（人工或 agent）。人工審查可滿足獨立條件；同一 agent 或同一上下文的自評不得標為獨立審查。
5. `full_pipeline + cross-check` 可由最終獨立結果審查滿足，不必為同一目的重複增加 reviewer；`fast-lane + cross-check` 仍保留使用者明確要求的成果審查。
6. 小任務一旦出現重大衝突或超出原範圍，重新評估路線；涉及需求或授權邊界的變更，先取得使用者決定。
