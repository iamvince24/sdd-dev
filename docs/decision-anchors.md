# 決策的落點

只在需要查細節時載入這份文件；日常規則摘要見 `../README.md`。

`00-spec.md` 的偏離表和 `notes.md` 的決策理由表擋掉了大部分情況，但還有幾種決策
過去只活在對話裡。它們各自的落點如下，**沒有落點的決策不算做完**。

判準是一句話：**「如果這個 session 現在斷掉，下一個 session 讀檔案能不能還原這個決策？」**
不能，就是還沒寫完。

## AC 的來源標記

`00-spec.md` 第 4 節每條 AC 行尾要標 `[U]`（使用者拍板）／`[S]`（規格文件推得）／
`[C]`（Claude 推論、未確認）。沒有標記的話，下個 session 看 20 幾條 AC 全部同等權威，
**分不出哪條可以自行調整、哪條必須先問** —— 而這個差別只存在於當初那次對話。

`[C]` 必須同時出現在第 9 節問答紀錄；還有 `[C]` 未轉正就不進 G1。
`coverage-lint.js` 會自動掃出殘留的 `[C]`，不用人工逐條檢查。

**`[U]` 要帶回指**：寫成 `[U:Q3]`，指回第 9 節那條問答。`[C]` 規定要出現在第 9 節，
但轉正成 `[U]` 之後那條線就斷了 ——「這條是使用者親口說的」變成只有當初那次對話知道。
`coverage-lint.js` 會驗回指指得到一條狀態為 `answered` 的問答；舊格式 `[U]` 仍接受，只提醒。

## 問答紀錄不刪除

第 9 節的問題被回答後改狀態為 `answered`、把回答原文填進去，**不要刪除該列**。
問題本身沒價值，但「這條需求是使用者親口說的、原話是這樣」有價值。
清空之後留下的只有需求本文，來源就救不回來了。

## 核准綁內容

Gate 核准的是**某一份內容**，不是「這個項目」。被核准的檔案之後改了實質內容，該 Gate 失效，
要重新過。

以前這件事綁的是人手寫的版本號，而那有個安靜的破口：**改了 AC 但忘記升版時，
版本比對會通過**。現在綁的是 `notes.md` Gate 狀態表「核准指紋」欄裡的**語意指紋** ——
核准時跑 `gate-guard.js <項目> --print-fingerprint` 取得後貼上，之後由腳本直接比內容。
版本號欄保留給人讀。

不這樣做的話，`01-plan.md` 已經 v6、核准的到底是哪一份，就只剩我記得。

指紋的取值範圍與豁免規則見 `automation.md`；腳本唯讀，不會自己把指紋寫進檔案。

### 收尾白名單（哪些修改不使核准失效）

光有「核准綁內容」會缺一條配對規則：**「改了一個錯字要不要重跑 G2」**。
只寫「例外是純錯字」的話那還是一道判斷題，每次都要重新辯論一次。下面是查表題 ——
而且多數情況現在是**自動**成立的，因為指紋本來就不涵蓋那些部分：

**不使已通過的 Gate 失效**：

| 修改 | 怎麼成立 |
| --- | --- |
| 只改 `notes.md`（進度、決策理由、審查紀錄） | 自動（指紋不讀 `notes.md`） |
| 只改 `02-tasks.md` 的「狀態」欄（`todo` → `wip` → `done` → `blocked`） | 自動（指紋排除狀態欄） |
| 只在 `03-verify.md` 補證據，未改變任何狀態值 | 自動（指紋不讀 `03-verify.md`） |
| 只改修訂紀錄本身、排版、換行重排 | 自動（指紋排除修訂紀錄，且正規化後不受換行影響） |
| **AC／決策本文的純錯字** | **仍需人工**：在該檔修訂紀錄註明「不影響核准」，並更新指紋欄 |

**一律使 Gate 失效**：任何 AC、設計決策、`INV-n`、任務範圍、狀態值的變動。
文件之間的失效關係見 `../README.md` 的失效鏈表 —— 其中「`00-spec.md` 升版 →
`03-verify.md` 已填的列失效」那一條，由 `03-verify.md` 每列的「驗證時 spec 指紋」欄
自動判成 `STALE`。

還有一條自我保護：**同一份未改動的文件被反覆送去審查時，停下來回報這是流程缺陷**，
不要再送一次。若使用者或執行環境另外設定審查回合上限，以該次工作階段明確提供的設定為準；
公開工具不依賴任何人的 home directory 或未進版控的全域指令檔。

## 獨立審查紀錄

每次 `plan-verifier`／`verifier`／`security-reviewer` 的結果都要在 `notes.md` 的
獨立審查紀錄表留一列：審查對象＋版本、verdict、提出的 blocker、我判成
`FIX`／`DEFER`／`REJECT` 的理由。

**只寫「審為 READY」是不夠的** —— 被駁回的內容與處置理由才是下次改計劃時真正需要的東西，
不寫下來就會重犯已經被指出過的問題。

Tier L 專案的 G2／G3，`gate-guard.js` 會強制檢查這張表有沒有對應的完整一列，
沒有就不能視為 Gate 有效核准。

## 驗證證據要能離線重現

`03-verify.md` 的證據欄不接受「目視確認 OK」這種句子。要貼回應片段、指令輸出、
`file:line`、commit hash，或把截圖存成 `refs/evidence/<AC 編號>-<描述>.png` 再填路徑。
證據如果只存在於當時的對話，G3 就無法被重新檢查。

每列還要填**驗證當下的 spec 指紋**（回歸風險表填 plan 指紋）。證據能不能重現是一回事，
「它證明的是哪一版需求」是另一回事 —— 少了這一欄，`00-spec.md` 改過之後那些列在機器眼中
完全正常。`verify-evidence-lint.js` 會把對不上的列判成 `STALE`。

`verify-evidence-lint.js` 也會自動挑出疑似敘述性的證據，見 `automation.md`。

## 跨項目知識搬去 `refs/`

發現「這個 repo 的陷阱」（不可照抄的範本、共用程式碼的怪行為、命名與文件相反）時，
記在 `notes.md` 的讀過檔案表，**歸檔前搬進 `refs/codebase-gotchas.md`**。
那是 repo 的知識不是需求的知識，跟著項目進 `done/` 等於埋掉。

已知的陷阱會被 `coverage-lint.js` 拿來跟任務的「檔案」欄自動比對，
命中但任務沒填「關聯 Gotcha」欄時會被提醒。

## 不能弄壞什麼要有編號

`01-plan.md` 第 6 節的 `INV-n` 是「這次不能弄壞什麼」的落點，`03-verify.md` 的
回歸風險表用**同一組 ID** 驗它。三段式：起始條件、可觀察結果、失敗條件。

不這樣做的話，「其他共用頁面的頁首沒壞」這件事在整套流程裡沒有任何落點 ——
它不是任何一條 AC，不會出現在 `03-verify.md` 的逐條表，最多在回歸風險表寫一行散文，
而散文沒辦法被對帳。`refs/codebase-gotchas.md` 存在的理由，就是「靠寫 plan 的人當下記得」
這件事已經靠不住了。

任務的「關聯 Gotcha」欄只證明**讀過**那條記錄，`INV-n` 才證明**會驗**它有沒有被弄壞。

## 中斷點細到任務內部

`02-tasks.md` 狀態欄有 `wip`：開始動一個任務就先標上，並在 `notes.md`「進行中」
寫一行「做到哪、下一步是什麼」。只有 `todo`／`done` 的話，寫到一半被中斷、
又還沒 `git add`，那段進度沒有任何落點。

想快速還原到這個狀態，跑 `snapshot.js`，見 `automation.md`。
