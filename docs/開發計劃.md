## 1. 現況

`HEAD` 是 local-first 的 `devplan`：

- 工具 clone 自帶私有 state：`state/projects/<repo-id>/active/<item>/`
- 設定在工具根的 `devplan.local.json`，路徑相對工具根
- 產物是 `00-spec` / `01-plan` / `02-tasks` / `03-verify` / `notes`，Gate 為 G1／G2／G3
- 分級是 Tier S／M／L
- `devplan check` 只讀 markdown。lint、test、build、瀏覽器都不會跑
- 證據綁 spec 語意指紋，不綁程式碼 SHA
- 整合只有 Claude Code hook
- package `devplan-local`，bin `devplan`，MIT，零 runtime npm 依賴，Node `>=16`
- npm 名稱 `devplan` 已被佔用

工作區已把上述檔案全部刪掉（未 stage）。依 D-0，舊架構不保留；只有 P0 列出的檔案從 `HEAD` 撿回。舊碼要查時用 `git show b00edf7:<path>`。

新需求改掉的是產品形狀，不是把模板換標題：

| 舊 | 新 |
| --- | --- |
| state 永遠在工具 repo、一律不進版控 | 各目標 repo 的 `.sdd-dev/`；版控由該 repo 使用者選 |
| 只有 shared clone | `repo-local`（`.sdd-dev/tool/`）或 `shared-sibling` |
| 一個 item 四份模板 | 一次 run：`.sdd-dev/runs/<run_id>/` |
| Tier S／M／L、人人過 G1／G2／G3 | `direct`／`selected_advisors`／`full_pipeline`，外加 fast-lane、cross-check、no delegation、plan-only |
| `D1` = 設計決策 | `D1`–`D7` = 計畫審查維度 |
| 核准綁人手版本 + 指紋，寫在 `notes.md` | `artifact_revision`；被核准或審查引用的內容不可覆寫；沿用核准要有影響評估 |
| G3 用 regex 判斷「證據長得像證據」 | 真的跑驗證；狀態只有通過、失敗、未執行、受阻 |
| 模型寫死在流程文字 | 角色對模型的對應在設定檔 |
| 只有 hook，沒有角色指令 | 一份中性角色指令，由各平台 adapter 產生 |

## 3. 目標架構

公開 repo 只放可重用工具、中性模板、假資料測試、平台 adapter。真實專案的 spec、證據、路徑、公司詞彙留在該 repo 的 `.sdd-dev/`，而且秘密值不進設定、日誌、證據。

```
sdd-dev/                          # 公開工具
  bin/sdd.js
  lib/                            # 純函式，checker 可被測試直接 require
  templates/run/
  templates/roles/                # P10 中性角色指令
  templates/routes/
  integrations/
    claude-code/
    cursor/
    codex/
  tests/

<target-repo>/.sdd-dev/
  tool/                           # 只有 repo-local
  config/
    install.json                  # 只放相對路徑，可進版控
    install.local.json            # 解析後的絕對路徑，永遠被 git 忽略
    workspaces.json
    models.json
    policy.json
  runs/<run_id>/
    manifest.json
    sources/                      # 貼上或口述的需求存成檔再算 hash
    clarify/state.md
    clarify/decisions.md
    spec/execution-spec.md
    spec/revisions/rN.md          # 被引用後凍結
    spec/impact/rN.md             # 沿用核准時的影響評估
    plan/plan.md
    plan/revisions/rN.md
    plan/impact/rN.md
    review/plan-review-rN.md
    review/result-review-rN.md
    approvals/spec.json
    approvals/plan.json
    context/<role>[-<T-n>].json   # 角色輸入清單
    tasks/tasks.md
    problems.md
    scratch/                      # 確認需求階段的實驗、暫存 worktree
    evidence/<ac-id>/
    evidence/baseline/
    metrics.json
    report.md
```

`shared-sibling`：工具在目標 repo 的同層，各 repo 只有 `config/` 與 `runs/`。`install.json` 只記 mode 與工具相對於 repo 根的路徑；解析後的絕對路徑放 `install.local.json`，避免 `.sdd-dev/` 進版控時洩漏本機路徑，也讓協作者各自解析。不把 A repo 的 run 寫進共享工具目錄。共享安裝的工具檔不跟著某個目標 repo 的「`.sdd-dev/` 要不要進版控」一起被決定。

`repo-local`：工具在該 repo 的 `.sdd-dev/tool/`，是否進版控跟著該 repo 的選擇。

不論哪種模式、選 track 或 ignore，`.sdd-dev/config/*.local.json` 一律寫進忽略規則。

### 3.1 機器讀的鍵

檢查器讀 frontmatter、JSON 鍵與章節標記，不讀中文標題。內文可以是繁體中文。

Execution Spec、Plan、正式審查報告：

```yaml
---
artifact: execution-spec   # execution-spec | plan | plan-review | result-review
run_id: 20260926-a1b2
revision: 1
content_hash: sha256:...
change_summary: 初版
source_refs:
  - path: docs/foo.md
    id: sha256:...          # 無版本號時用內容雜湊
based_on:                   # 只有 plan 與審查報告
  artifact: execution-spec
  revision: 1
  content_hash: sha256:...
status: draft               # draft | approved | superseded
---
```

章節以 `<!-- sec:<key> -->` 標記，checker 依標記切段算 diff。必要標記缺少就失敗。

- Spec 的鍵：`sources`、`clarifications`、`scope`、`exclusions`、`constraints`、`interfaces`、`assumptions`、`deviations`、`requirements`、`acceptance`
- Plan 的鍵：`goals`、`scope`、`constraints`、`decisions`（AD）、`interfaces`、`paths`、`dependencies`、`tasks`、`verification`、`notes`

不可沿用段（D-8），diff 碰到就必須重新核准：

- Spec：`scope`、`exclusions`、`constraints`、`interfaces`、`requirements`、`acceptance`
- Plan：`scope`、`constraints`、`decisions`、`interfaces`、`paths`、`dependencies`、`verification`

`manifest.json` 至少有：

- `run_id`
- `policy_version`
- `route`：`direct` | `selected_advisors` | `full_pipeline`，等於 `route_history` 最後一筆
- `route_history[]`：`at`、`route`、`modifiers`、`reason`、`by`（`auto` | `user`）。第一筆是初始路線
- `modifiers`：`fast_lane`、`cross_check`、`no_delegation`、`plan_only`
- `platform`
- `models`：開始當下從 `models.json` 抄一份，不事後改歷史
- `sources[]`：每份來源各自的 `path` 與 `id`（版本或內容 hash）
- `workspaces[]`：`id`、`path`、`vcs`（`git` | `snapshot`）、`baseline`（branch、`codebase_ref`、baseline 的 dirty 路徑清單）
- `write_roots[]`
- `grants[]`（見 3.2）
- `capability_limits[]`：`op`、`layer`（`tool` | `platform` | `convention`）、`gap`
- `implementation_authorized`
- `status`：`active` | `awaiting_user` | `blocked` | `done` | `stopped`

`codebase_ref`（每個 workspace）：`head`（Git SHA）加 `worktree_hash`。`worktree_hash` 是 `git diff HEAD --binary` 與相關 untracked 檔內容合起來的 sha256，乾淨工作樹時為空。非 git 用工作樹內容 hash。不用 porcelain 輸出：它只列檔名，同一檔再改一次內容，輸出不會變。

`blocked` 不是路線。阻塞記在 `manifest.blocks[]`：`id`、受影響的需求／任務、解除條件、進入時間。同一項目重複回報不新增計數。run 的 `status` 只有在所有剩餘工作都受阻時才是 `blocked`；局部阻塞只記在 `blocks[]`，其他工作照跑。

核准檔：

```json
{
  "artifact": "plan",
  "revision": 3,
  "content_hash": "sha256:...",
  "based_on_spec": { "revision": 2, "content_hash": "sha256:..." },
  "approved_at": "2026-09-26T00:00:00+08:00",
  "carried_from": { "revision": 2, "impact": "plan/impact/r3.md" },
  "auto_commit": false
}
```

`carried_from` 沒沿用時為 `null`。`based_on_spec`、`auto_commit` 只有 plan 有。

核准規則：

- 被核准或被審查引用的 `revisions/rN.md`，之後 hash 變了，檢查直接失敗。現行檔可以改；一被引用，就先凍結複本再改下一版。
- 核准有效的條件：核准的 hash 等於現行 revision，或有一條 `carried_from` 鏈接到現行 revision，且每一段都通過沿用檢查。
- 沿用檢查：`impact/rN.md` 逐段列出兩版之間有 diff 的章節鍵，每段寫「影響：無」與理由。checker 用章節標記重算 diff；impact 漏列任何一段就失敗；diff 碰到不可沿用段也失敗。
- 沿用紀錄列在 report 的「沿用核准」段。使用者推翻時，該 revision 的核准標無效，走正常核准。
- Plan 核准綁 `based_on_spec`。Spec 換 revision 後，plan 要出一版 `based_on` 指向新 spec 的新 revision；plan 內容沒受影響時可以沿用核准，有影響就重審、重核。
- 審查結果的沿用規則與核准相同。

### 3.2 權限邊界

每次 `run start` 與 `run resume` 都重算 git 基準，不沿用舊的 `codebase_ref`。基準變了，先標受影響的任務、核准、證據，不自動宣告影響範圍以外的東西也失效。

強制點分三層（D-10）：

| 層 | 由誰擋 | 範圍 |
| --- | --- | --- |
| `tool` | `sdd` 自己 | 經由 `sdd` 的操作：`sdd commit`、`sdd update --apply`、`sdd uninstall`、寫 `runs/` |
| `platform` | 平台 hook（Claude Code `PreToolUse`、Cursor hooks 等，P7 實測） | agent 直接跑的 shell 指令：`git reset --hard`、force push、刪寫入範圍以外的檔、直接 `git commit` |
| `convention` | 只有角色指令 | 前兩層都做不到的部分 |

每個 op 實際落在哪一層，由 P7 的矩陣決定，寫進 `capability_limits[]`。`policy.json` 的 `required_enforcement` 列出這次必須由 `tool` 或 `platform` 層強制的 op，預設為空，使用者可以加。列入的 op 落在 `convention` 層時，受影響工作維持 `blocked`；沒列入的，照流程約定繼續，但 report 要寫明缺口。不把 `convention` 寫成已隔離。

授權（D-11）記在 `manifest.grants[]`：

- `id`（`G-n`）、`op`、`scope`（branch、路徑 glob、資料庫或服務名稱）、`source`（使用者回覆的 `Q-n`）、`granted_at`
- `op` 枚舉：`reset_hard`、`force_push`、`history_rewrite`、`delete_outside_roots`、`prod_write`、`external_data_write`、`dependency_install`、`lockfile_change`、`network`
- 只在該 run 有效。同一 `op`、且 scope 涵蓋的操作不再詢問
- Plan 核准不推定任何 grant
- 不記憑證、token、連線字串，只記能力與用途

寫入範圍（D-12）：

- 目標 repo 的 `.sdd-dev/runs/<run_id>/`，含 `scratch/`
- 該次任務聲明的產品碼路徑（plan 核准後）
- profile `verify[].outputs` 宣告的路徑（例如 `dist/`、`coverage/`），只限驗證指令產生
- `repo-local` 的 `.sdd-dev/tool/`，只限 `sdd update --apply`
- 其他（安裝依賴、改 lockfile、連網、外部服務）要有對應 grant

確認需求階段的實驗只寫 `scratch/`。要在產品碼上試，就在 `scratch/` 下開暫存 `git worktree`，結束時移除。這條邊界對所有角色與階段都一樣，包括 scout 的實驗與 verifier 重跑。

執行前已存在的修改：baseline 的 dirty 路徑與任務責任路徑相交時，該任務必須填 `preexisting_overlap: separable|blocked` 與理由。`blocked` 只擋該任務與它的下游。同一檔同時有 baseline 修改與本次修改時，`sdd commit` 拒絕該檔並交給使用者，不嘗試拆 hunk。

秘密：日誌與證據寫入前，掃描常見的憑證形狀（金鑰、`Authorization`、`.env` 賦值）。掃到就改寫成 `[redacted]`，並在問題清單記一筆。掃不到的不假裝已隔離。證據的執行條件只記環境變數名稱，不記值。

### 3.3 選路

政策放 `config/policy.json`，版本寫進每次 run。內容是 r5 的表，不是再發明一套 Tier。

自動選路只填建議與理由，寫進 `route_history`。使用者指定的路線、核准點、`no_delegation` 優先。選路不擴大「可以改產品碼」的授權。`sdd run start --route` 接受 `ag`、`agentflow` 當作 `full_pipeline` 的別名。

| 路線 | 工具必須擋住的事 |
| --- | --- |
| `direct` | 沒有簡短 spec 紀錄、沒有驗收對任務、沒有證據，不能標完成。有 `cross_check` 時，另要有 result review |
| `selected_advisors` | 沒有實作授權。產品碼相對 baseline 出現新 diff 就失敗 |
| `full_pipeline` | 沒有對應 revision 的 spec 核准，不能建立 plan；沒有 plan 核准，不能把任務標成 `in_progress`；沒有 result review，不能標 `done` |
| `full_pipeline` + `fast_lane` | 同上。精簡的是篇幅，不是核准、獨立審查、驗證 |
| `full_pipeline` + `cross_check` | 由最終 result review 滿足，不另加 reviewer |
| `plan_only` | plan 通過審查（`direct`：plan 寫完）就設 `awaiting_user`，不開執行任務；使用者核准 plan 後回 `active` |
| `no_delegation` | `reviewer_kind: agent` 的審查不能標 `independent: true`。要獨立就由 `reviewer_kind: human` 完成，或使用者解除 `no_delegation`（記進 `route_history`）後再派 agent |
| `no_delegation` + `cross_check` | 不啟動第二個 agent。result review 維持 `pending_human` |

`full_pipeline` 升級不清除未知、驗證能力不足、或未授權。該 `blocked` 繼續 blocked。

重新評估路線：`sdd check` 發現產品碼 diff 超出 plan 的 `paths`，或新增 blocking 的 Conflict 時，回報 `route_reassess`。是否升級、理由都寫進 `route_history`；牽涉需求或授權邊界的，先問使用者。

獨立審查（D-9）：

- `reviewer_kind: human`：使用者或使用者指定的人，滿足獨立條件。記 `reviewer`（角色名稱，不記聯絡資訊）與時間
- `reviewer_kind: agent`：`context_id` 必須和 planner／executor 的不同，且平台矩陣支援獨立委派，才能寫 `independent: true`
- 同一 agent 自評一律 `independent: false`

計畫審查自動修訂預設 2 輪（`policy.max_revise_rounds`）。一輪 = 一次修改 + 一次獨立重審。到頂仍有阻塞項就停，不刪需求。

審查報告每條問題要有：位置、依據、嚴重度、建議、解除條件、`blocking: true|false`。分數欄位可以有，但 checker 不拿來判定 `READY`。`READY` 只表示沒有未解阻塞，不是實作授權。不適用的 D 維度要有理由。安全、資料遺失、必要 migration 缺失、對外介面不相容，不能被其他維度抵銷。

Result review 依據 Execution Spec、實際 diff 與證據判定，不只看 executor 的完成宣稱。verifier 重跑的關鍵驗證也寫進 `evidence/`，綁定 `codebase_ref`。

### 3.4 驗證

Workspace profile（`workspaces.json`）記可執行指令、前置條件、已知限制：lint、型別、unit、integration、E2E、build。沒有指令就記 `absent` 與原因。初始化結果可重用；指令或規範變了只更新受影響段。git 狀態不放進這份可重用 profile。

AC 需要的能力在 profile 是 `absent` 時，plan 必須替該 AC 另排能證明同一條件的方法（smoke、瀏覽器、API、人工）；排不出來，該 AC 就是 `blocked`，不降標準。

`sdd verify` 做的事：

1. 照 profile 跑指令，stdout／stderr 寫進 `evidence/`，附 exit code、cwd、開始結束時間、`codebase_ref`、`requires` 裡列的工具版本、用到的環境變數名稱。
2. 比對該驗收列要求的方法與通過條件。指令 exit 0 只證明那條指令過了。
3. 瀏覽器、API、人工若沒有證據檔，狀態維持 `not_run`。禁止從「檔案改了」推成 `pass`。

既有失敗（D-15）：

- 只認 `evidence/baseline/` 裡綁 baseline `codebase_ref` 的證據。profile 的 `known_failures` 只是提示。
- `run start` 時，對 `known_failures` 有列的指令先跑一次，存成 baseline 證據。
- 事後才補跑的，只能在 baseline HEAD 的暫存 worktree 跑。baseline 本身有未提交修改時，這個結果不等於 baseline，不能用，維持 `blocked`。
- 可以標 `preexisting` 的條件：baseline 證據同樣失敗、本次的失敗集合沒有比 baseline 多（比對失敗的測試名或錯誤清單；比不出來視同無法確認）、本次必要 AC 另有自己的證據。任一條件不成立就維持 `blocked`。

證據的 `codebase_ref` 與目前的 HEAD 或 `worktree_hash` 不一致，該列標 `stale`，不算通過。

### 3.5 角色輸入

不把整包 run 丟給每個角色。`sdd context --role <role> [--task T-n]` 產生 `context/<role>[-T-n].json`：每一項是路徑、revision、ID、`codebase_ref`。角色可以在讀寫邊界內自己打開原始檔。

每個角色都有的共同內容：`workspaces.json` 的 `conventions`、`write_roots`、`grants`、`capability_limits`、使用者限制（`modifiers` 與 clarify 裡標為限制的項目）。

| 角色 | 預設路徑 |
| --- | --- |
| scout | 來源 spec、探索問題（clarify 的 Unknown）、`clarify/state.md`、workspace profile、本次 git 基準 |
| planner | Execution Spec（`full_pipeline` 限已核准 revision）、clarify、profile（驗證能力）、介面摘錄 |
| plan-reviewer | Execution Spec、Plan、政策裡的 D1–D7、專案限制、codebase 路徑。不附 planner 對話 |
| executor | 單一任務、對應 spec／plan 段落、驗收 ID、檔案責任、依賴、驗證方法 |
| security-reviewer | 相關需求、設計（plan 的 `decisions` 與 `interfaces`）、diff、資料流、信任邊界、證據 |
| verifier | 驗收列、完成宣稱、diff、`codebase_ref`、證據目錄、執行條件 |

reviewer 與 verifier 的清單只放 planner／executor 的完成宣稱與正式報告路徑，不放對話。清單裡任一來源的 revision 或 `codebase_ref` 變了，`sdd check` 就把該清單標 `stale`，重新產生之前不能拿來派工。

`models.json` 只放角色到模型 id。流程碼與角色指令不出現模型名稱字串。空值表示用平台當下的模型。Pilotfish 不在這階段進依賴。

### 3.6 量測

`metrics.json` 跟 run 走，不上傳。缺值寫 `unknown`，不寫 0。

| 類別 | 欄位 |
| --- | --- |
| 識別 | `run_id`、`policy_version`、`platform`、`models` |
| 選路 | `route_initial`、`route_final`、`escalations[]`（附原因）、`risk_features[]`，由 `route_history` 導出 |
| 成本 | `clarifications`、`plan_revise_rounds`、`blocks`、`subagents`、`approvals`、`approval_requests`、`active_ms`、`waiting_ms` |
| 驗證 | `first_pass_success`、`final_pass_success`、`not_run[]`、`blocked[]` |
| 人工決策 | `approvals_changed_outcome`（核准時是否帶來需求、設計、風險的變更）、`overrides[]`（使用者覆寫流程建議，附原因） |
| 後續 | `outcomes[]`：`kind`（`rework` \| `reopen` \| `revert`）、`observed_at`、`basis` |

`waiting_ms` 是 run 處於 `awaiting_user` 或 `pending_human` 的時間。沒追蹤到後續結果時，`outcomes` 是 `unknown`，不是空陣列。run 結束後，用 `sdd metrics outcome --run <id>` 補記後續結果。

計數定義照 r5：澄清＝一次使用者回覆請求；修訂輪＝審查定義的一輪；阻塞＝項目進入 blocked 的事件；subagent＝實際建立數；核准＝使用者真的核准，與核准請求分開。

`first_pass_success`：該需求 revision 的必要驗收各自第一次就是 `pass`，且沒有 `not_run`／`blocked`。revision 一變，舊指標留著，不覆蓋。`final_pass_success` 看目前證據。兩者都不取代獨立審查。

### P1 安裝與版控選擇

依賴：P0、D-1。

產出：

- `sdd init --mode repo-local|shared-sibling`
- `install.json`：mode、工具相對路徑、工具 content hash、來源版本（package version 或 git SHA）、config schema 版本、建立時間。絕對路徑只放 `install.local.json`
- `sdd config tracking track|ignore`
  - track：先列出將被追蹤的路徑清單讓使用者確認；仍寫 `.sdd-dev/config/*.local.json` 的忽略規則
  - ignore：寫或提示 `.gitignore` 規則，並跑 `git check-ignore` 與 `git ls-files .sdd-dev`。已追蹤檔只回報，不 `git rm`
- 非 git 目錄：記錄保存位置，`vcs: snapshot`，不宣稱有 git 隔離
- `sdd doctor`：路徑對應、模式與目錄是否一致、`install.local.json` 解析結果與實際位置是否一致（搬 repo、換模式後會抓到）、版控選擇與忽略規則是否一致、秘密檔名是否被放進工具 repo。不要求至少兩個 repo
- `sdd update`：印目前與目標的版本和 hash、受影響的 repo 與設定、需要的遷移（config schema 差異）。預設不執行，`--apply` 才換工具檔並跑遷移。不刪 `runs/`
- `sdd mode switch repo-local|shared-sibling`：搬工具檔、改 `install.json`，完成後自動跑 `doctor`
- `sdd uninstall`：只移除工具檔與 sdd 自己的 hook 條目；`config/`、`runs/` 保留，並印出保留的路徑。要刪除必須另給 `--purge`，列出清單讓使用者確認

實作決定（2026-09-26）：

- 確認一律用 `--yes`：track 的追蹤清單、`uninstall --purge` 的刪除清單，不帶 `--yes` 就只印清單並 exit 1，不寫任何檔。不用互動式提示
- 忽略規則只寫 `.sdd-dev/.gitignore`：ignore 模式內容是 `*`（連自己也被忽略），track 模式只寫 `config/*.local.json`。不動目標 repo 根目錄的 `.gitignore`
- `shared-sibling` 的 repo 清單記在共享工具被 git 忽略的 `sdd-dev.local.json` 的 `installs[]`，只存 repo 路徑。這個檔沒被忽略時，`init` 與 `mode switch` 直接拒絕
- git repo 裡的 `init` 必須給 `--tracking`，沒給就 exit 3。非 git 目錄不需要，記成 `vcs: snapshot`、`tracking: null`
- `mode switch` 切到相同模式只重新連結路徑，不換工具檔；換工具檔只能經由 `sdd update`
- `shared-sibling` 的工具檔由使用者自己更新（例如 `git pull`），`sdd update` 只能從該共享工具執行，並把新 hash 記進清單上的每個 repo

驗收：

- AC-P1-1 Given 空的 git repo，When `init --mode repo-local` 且選擇 ignore，Then `.sdd-dev/tool` 與 `config` 存在，`git check-ignore` 命中，`git status` 不出現這些檔。
- AC-P1-2 Given `.sdd-dev/config/install.json` 已被追蹤，When 選擇 ignore，Then doctor 失敗並列出已追蹤路徑，磁碟上的檔還在。
- AC-P1-3 Given 兩個 repo 共用同層工具，When 只在 A 寫入 run，Then B 的 `.sdd-dev` 與工具目錄都沒有 A 的檔。
- AC-P1-4 Given 已安裝，When `sdd update` 不帶 `--apply`，Then 工具檔 hash 不變。
- AC-P1-5 Given 已安裝且有 run，When `sdd uninstall`，Then `config/`、`runs/` 還在，且輸出列出這些路徑。
- AC-P1-6 Given 選 track，When 完成設定，Then 輸出列出將追蹤的路徑，且 `install.local.json` 被 `git check-ignore` 命中。
- AC-P1-7 Given `shared-sibling` 安裝後把 repo 搬到別的目錄，When `doctor`，Then 失敗並指出路徑對應不符。
- AC-P1-8 Given 目標版本的 config schema 比目前新，When `sdd update` 不帶 `--apply`，Then 輸出列出需要的遷移，設定檔不變。

不做：需求、計畫、驗證執行。

### P4 需求查核與 Execution Spec

依賴：P2。

產出模板與 `sdd check --stage spec`：

- `clarify/state.md` 六類：Current State、Target State、Expected Delta、Conflict、Unknown、Assumption。每條有 id、證據路徑、是否阻塞。Assumption 可以標 `overturned`，checker 列出引用它的 R、AC、T。
- `clarify/decisions.md`：問題、影響、選項、建議、回答、revision。已回答的不刪。
- Execution Spec 章節與標記見 3.1。驗收在進 plan 前就要有：Given／When／Then、`kind`（`normal` | `error` | `boundary`）、通過條件。驗證方法欄位先留空，P5 填。
- `deviations`：與原始 Spec 的每條差異，都要引用一個已回答的 `Q-n`。checker 只能檢查「已宣告的差異有沒有決策」；沒宣告的差異靠 plan-reviewer 的 D1、D3 抓。
- 追溯表骨架：`R` → `AC` → `T` → evidence。P4 允許 `T` 與 evidence 空著，但不允許沒有 AC 的 R。
- 沿用核准（D-8）：`spec/impact/rN.md` 的格式與沿用檢查。
- `full_pipeline`：spec 沒有有效核准時，`sdd plan new` 拒絕。
- `direct` 用同一 schema，檔可以短。檢查的是欄位在，不是字數。
- `selected_advisors` 只寫諮詢結論，`manifest.implementation_authorized` 維持 false。

驗收：

- AC-P4-1 Given spec 有 R 沒有 AC，When `check --stage spec`，Then 失敗。
- AC-P4-2 Given `full_pipeline` 且 spec 仍是 draft，When 把任務標 `in_progress`，Then 失敗。
- AC-P4-3 Given 使用者只核准 revision 1，現行 spec 已是 revision 2 且沒有 `carried_from`，When 檢查核准，Then 核准不被視為有效。
- AC-P4-4 Given `selected_advisors`，When 產品碼相對 baseline 出現新 diff，Then 失敗；baseline 就已有的修改不算。
- AC-P4-5 Given `full_pipeline` 且 spec 沒有有效核准，When `sdd plan new`，Then 拒絕。
- AC-P4-6 Given r2 只改了 `sources` 段且 impact 檔完整，When 檢查 r1 核准能否沿用，Then 有效。
- AC-P4-7 Given r2 改了 `acceptance` 段，When 用 `carried_from` 沿用 r1 核准，Then 失敗。
- AC-P4-8 Given impact 檔漏列一個有 diff 的段，When 檢查，Then 失敗。
- AC-P4-9 Given `deviations` 有一條沒引用 `Q-n`，When `check --stage spec`，Then 失敗。
- AC-P4-10 Given Spec 缺少必要的章節標記，When `check --stage spec`，Then 失敗。

### P5 計畫、審查、選路、角色輸入

產出：

- Plan 必要段與標記見 3.1；`verification` 段替每條 AC 填驗證方法
- 任務表：`T`、目的、擁有的路徑、`integrator`（整合負責者）、依賴、驗收 ID、commit 邊界、`preexisting_overlap`、狀態
- 審查報告 schema：`READY`／`REVISE`／`BLOCKED`、`reviewer_kind`、`context_id`、`independent`
- Plan 核准檔：`based_on_spec`、`auto_commit: false|true`（預設 `false`）、`carried_from`。改 `auto_commit` 等於改核准內容，要重新核准
- `check --stage plan` 的檢查：
  - 兩任務的路徑集合相交且沒有順序依賴，就失敗
  - 有 R 沒有任何 T，就失敗
  - 任務路徑與 baseline dirty 路徑相交卻沒填 `preexisting_overlap`，就失敗
  - plan 的 `based_on` 不是現行有效的 spec revision，就失敗
- 任務狀態：依賴任務的必要檢查不是 `pass`，就不能 `in_progress`
- `plan_only`：plan 通過審查（`direct`：plan 寫完）就設 `awaiting_user`
- `sdd context`（見 3.5）
- `route_reassess` 偵測與 `route_history` 寫入

驗收：

- AC-P5-1 Given 兩個任務都列 `src/a.ts` 且沒有依賴，When `check --stage plan`，Then 失敗。
- AC-P5-2 Given `full_pipeline` 審查有未解的 blocking 安全項，When 請求 plan 核准，Then 失敗。
- AC-P5-3 Given `no_delegation`，When `reviewer_kind: agent` 的審查紀錄寫 `independent: true`，Then 失敗。
- AC-P5-4 Given 已滿兩輪修訂且仍有 blocking，When 再送自動重審，Then 命令拒絕且 spec 範圍沒被改。
- AC-P5-5 Given `fast_lane`，When 缺少 spec 核准、plan 核准或獨立計畫審查，Then 與非 fast-lane 的 `full_pipeline` 一樣失敗。
- AC-P5-6 Given 核准檔沒有 `auto_commit`，When 讀取，Then 視為 `false`。
- AC-P5-7 Given `no_delegation` 且 `reviewer_kind: human` 的審查是 `READY`，When 請求 plan 核准，Then 不因獨立條件失敗。
- AC-P5-8 Given T-2 依賴 T-1 且 T-1 的必要檢查不是 `pass`，When 把 T-2 標 `in_progress`，Then 失敗。
- AC-P5-9 Given `plan_only`，When plan 審查 `READY`，Then run 是 `awaiting_user` 且沒有任務是 `in_progress`；使用者核准 plan 後回 `active`。
- AC-P5-10 Given spec 升到 r3，plan 的 `based_on` 仍指 r2，When `check --stage plan`，Then 失敗並要求出新 plan revision。
- AC-P5-11 Given context 清單產生後 plan 出了新 revision，When `sdd check`，Then 該清單標 `stale`。
- AC-P5-12 Given 某 R 沒有任何 T，When `check --stage plan`，Then 失敗。
- AC-P5-13 Given T-1 的路徑與 baseline dirty 路徑相交且沒填 `preexisting_overlap`，When `check --stage plan`，Then 失敗。

不做：派出真的 subagent。這階段只定義紀錄與非法組合。真的委派在 P7、P10，而且平台做不到就維持 `pending_human`。

### P6 開發紀錄、真實驗證與結果審查

依賴：P3、P5、D-15。

產出：

- 問題清單 `problems.md`：`P-n`、影響、處理、理由、結果、是否阻塞下游。阻塞下游的項目要解除，必須附解決證據（證據路徑或 commit）；只有紀錄或 TODO 不算
- `sdd verify --ac <id>`：跑 profile 裡對上的指令，或接受已存在的證據檔（人工／瀏覽器／API）
- 狀態枚舉只有 `pass` | `fail` | `not_run` | `blocked`。另加屬性 `stale`、`preexisting`，不是第五種通過
- baseline 證據的產生與 `preexisting` 判定（見 3.4）
- `sdd check --stage dev`：比對相對 baseline 的 diff 與寫入範圍（任務路徑、profile outputs）；超出就失敗並回報 `route_reassess`。`auto_commit: false` 時也適用
- Result review：`review/result-review-rN.md`，套用 D-9；verifier 重跑的證據存進 `evidence/`
- 完成條件：run 要標 `done`，所有必要 AC 都要 `pass`（或 `preexisting` 且本次有自己的證據），沒有 `stale`，且路線要求的 result review 是 `READY`
- 最終 `report.md`：完成、證據路徑、沿用核准、剩餘、延後、能力缺口。延後必須有理由，預設不延後
- 整合檢查清單：任務各自的檢查、整合檢查、最終驗收分開列
- `sdd commit --task <T-n>`：唯一給 agent 用的 commit 入口。條件：
  - plan 核准有效且 `auto_commit: true`
  - 該任務的必要檢查都是 `pass`，且證據的 `codebase_ref` 對應目前工作樹
  - staged 路徑都在該任務的責任路徑內；執行前已存在的修改不能混進來，同一檔同時有 baseline 修改與本次修改就拒絕
  - 只做新 commit。不做 `--amend`、rebase、push
  - 不符合就 exit 1，工作區不動
- `auto_commit: false` 時，report 列出建議的 commit 邊界與訊息，由使用者自己 commit

驗收：

- AC-P6-1 Given profile 有會失敗的 `node -e 'process.exit(1)'`，When verify，Then 該 AC 為 `fail`，證據檔有 exit code，report 不能寫整體完成。
- AC-P6-2 Given AC 的方法是 `manual` 且證據目錄是空的，When 產生 report，Then 狀態是 `not_run`。
- AC-P6-3 Given 指令在 baseline 已經失敗且有 baseline 證據，本次的失敗清單與 baseline 相同，When verify，Then 可標 `preexisting`，且本次必要 AC 仍要另有自己的證據。
- AC-P6-4 Given 只有 profile 的 `known_failures`、沒有 baseline 證據，When 把失敗標成 `preexisting`，Then 檢查失敗。
- AC-P6-5 Given `auto_commit: false`，When `sdd commit --task T-1`，Then exit 1，`git log` 不變。
- AC-P6-6 Given `auto_commit: true` 且 staged 檔有一個不屬於 T-1，When `sdd commit --task T-1`，Then exit 1，`git log` 不變。
- AC-P6-7 Given `auto_commit: true`、T-1 檢查通過、staged 只含 T-1 路徑，When `sdd commit --task T-1`，Then 新增一個 commit，HEAD 的父節點是原 HEAD，遠端不變。
- AC-P6-8 Given `full_pipeline` 所有 AC 都 `pass` 但沒有 result review，When 標 `done`，Then 失敗。
- AC-P6-9 Given result review 是 `reviewer_kind: agent` 且 `context_id` 等於 executor 的，When 標 `done`，Then 失敗。
- AC-P6-10 Given 本次的失敗比 baseline 多一個測試，When 標 `preexisting`，Then 失敗。
- AC-P6-11 Given diff 含任務路徑以外的產品碼檔，When `check --stage dev`，Then 失敗並回報 `route_reassess`。
- AC-P6-12 Given 某檔在 baseline 就已修改、本次又改，When `sdd commit` 含該檔，Then exit 1，`git log` 不變。

`sdd commit` 只管「經由工具」的 commit。agent 直接跑 `git commit` 屬於 `platform` 層，要靠平台擋，能不能擋由 P7 的矩陣回答；擋不住就落在 `convention` 層並記為缺口，不宣稱已強制。

產品行為對不對，由目標 repo 的指令與證據判定。`sdd` 不重做一套 lint。

## 7. 風險

- 舊碼只剩 `b00edf7`。這個 commit 目前只在本機，比 `origin/main` 多 2 個 commit。本機 repo 若遺失，舊碼與 proposals 一起消失；要保留就先 push `main`。
- 刪除 commit 必須跟新增分開（P0 commit 切法第 1 步），否則 diff 無法 review。
- D-2 的「不能 commit」只在經由 `sdd commit` 時由工具強制。平台擋不住直接 `git commit` 時，落在 `convention` 層，不是隔離。
- 獨立審查在單 agent 平台上不可證明。工具只能拒絕假的 `independent: true`，不能製造第二個上下文；人工審查是這類平台唯一的獨立來源。
- 沿用核准依賴章節標記。標記放錯段，diff 判斷就會失準；checker 只擋得住「缺標記」，擋不住「標記錯位」，這靠 plan-reviewer 與使用者看 report。
- `worktree_hash` 要讀所有相關 untracked 檔內容。大型 untracked 檔會拖慢每次檢查，P2 需要依 `.gitignore` 與大小上限過濾，超過上限的檔要記成 `unknown`，不能默默略過。
- 事後補跑 baseline 只在 baseline 乾淨時有效。使用者在 run 開始前就有大量未提交修改時，既有失敗很可能只能判為 `blocked`。
- 自動選路的觸發（影響範圍、可回復性）沒有可靠的靜態判定。v1 讓 scout 填證據清單，人可覆寫；不寫「看檔案數」的啟發式當門檻。
- 憑證掃描會漏。漏了就當缺口，不把「已掃描」寫成「已安全」。

## 8. 實作切法

先做 P0，讓 `npm test` 與 `npm run privacy-check` 在空樹上跑得起來。之後第一個可跑的垂直切片是 P1 + P2 + P4 的 `direct`：假 repo 裡能 init、開 run、寫簡短 spec、檢查「有 AC、核准 hash 沒被改、秘密被遮」。這條切片綠了之後，接上 P10 的 `direct` 指令，讓三個平台都能實際走一次 `direct`（標 `verified: false`）。P5 的 `full_pipeline` 在這之後再加。P6 接上真的指令執行與 result review。P7 不阻塞 `direct`。

公開工具的 privacy scan 在每次要 commit 工具碼之前跑。掃描對象是工具 repo 自己，不是使用者的 `.sdd-dev/runs/`。
