## 1. 現況

`HEAD` 是 local-first 的 `devplan`：

- 工具 clone 自帶私有 state：`state/projects/<repo-id>/active/<item>/`
- 設定在工具根的 `devplan.local.json`，路徑相對工具根
- 產物是 `00-spec` / `01-plan` / `02-tasks` / `03-verify` / `notes`，Gate 為 G1／G2／G3
- 分級是 Tier S／M／L
- `devplan check` 只讀 markdown。lint、test、build、瀏覽器都不會跑
- 證據綁 spec 語意指紋，不綁程式碼 SHA
- 整合只有 Claude Code hook
- package `devplan-local`，bin `devplan`，MIT，零 runtime npm 依賴，Node `>=16`
- npm 名稱 `devplan` 已被佔用

工作區已把上述檔案全部刪掉（未 stage）。依 D-0，舊架構不保留；只有 P0 列出的檔案從 `HEAD` 撿回。舊碼要查時用 `git show b00edf7:<path>`。

r4 改掉的是產品形狀，不是把模板換標題：

| 舊 | r4 |
| --- | --- |
| state 永遠在工具 repo、一律不進版控 | 各目標 repo 的 `.sdd-dev/`；版控由該 repo 使用者選 |
| 只有 shared clone | `repo-local`（`.sdd-dev/tool/`）或 `shared-sibling` |
| 一個 item 四份模板 | 一次 run：`.sdd-dev/runs/<run_id>/` |
| Tier S／M／L、人人過 G1／G2／G3 | `direct`／`selected_advisors`／`full_pipeline`，外加 fast-lane、cross-check、no delegation、plan-only |
| `D1` = 設計決策 | `D1`–`D7` = 計畫審查維度 |
| 核准綁人手版本 + 指紋，寫在 `notes.md` | `artifact_revision`；被核准或審查引用的內容不可覆寫 |
| G3 用 regex 判斷「證據長得像證據」 | 真的跑驗證；狀態只有通過、失敗、未執行、受阻 |
| 模型寫死在流程文字 | 角色對模型的對應在設定檔 |

## 3. 目標架構

公開 repo 只放可重用工具、中性模板、假資料測試、平台 adapter。真實專案的 spec、證據、路徑、公司詞彙留在該 repo 的 `.sdd-dev/`，而且秘密值不進設定、日誌、證據。

```
sdd-dev/                          # 公開工具
  bin/sdd.js
  lib/                            # 純函式，checker 可被測試直接 require
  templates/run/
  integrations/
    claude-code/
    cursor/
    codex/
  tests/

<target-repo>/.sdd-dev/
  tool/                           # 只有 repo-local
  config/
    install.json
    workspaces.json
    models.json
    policy.json
  runs/<run_id>/
    manifest.json
    clarify/state.md
    clarify/decisions.md
    spec/execution-spec.md
    spec/revisions/rN.md          # 被引用後凍結
    plan/plan.md
    plan/revisions/rN.md
    review/plan-review-rN.md
    approvals/spec.json
    approvals/plan.json
    tasks/tasks.md
    problems.md
    evidence/<ac-id>/
    metrics.json
    report.md
```

`shared-sibling`：工具在目標 repo 的同層，各 repo 只有 `config/` 與 `runs/`。`install.json` 寫工具絕對路徑的解析結果與對應 repo，不把 A repo 的 run 寫進共享工具目錄。

`repo-local`：工具在該 repo 的 `.sdd-dev/tool/`。共享安裝的工具檔不跟著某個目標 repo 的「`.sdd-dev/` 要不要進版控」一起被決定。

### 3.1 機器讀的鍵

檢查器讀 frontmatter 與 JSON 鍵，不讀中文標題。內文可以是繁體中文。

Execution Spec、Plan、正式審查報告：

```yaml
---
artifact: execution-spec   # execution-spec | plan | plan-review | result-review
run_id: 20260926-a1b2
revision: 1
content_hash: sha256:...
source_refs:
  - path: docs/foo.md
    id: sha256:...          # 無版本號時用內容雜湊
status: draft               # draft | approved | superseded
---
```

`manifest.json` 至少有：

- `run_id`
- `policy_version`
- `route`：`direct` | `selected_advisors` | `full_pipeline`
- `modifiers`：`fast_lane`、`cross_check`、`no_delegation`、`plan_only`
- `platform`
- `models`：開始當下從 `models.json` 抄一份，不事後改歷史
- `workspaces[]`：`id`、`path`、`vcs`（`git` | `snapshot`）、`baseline`（branch、HEAD、porcelain、相關 untracked 的快照 id）
- `write_roots[]`
- `capability_limits[]`：平台強制 vs 流程約定，分開記
- `status`：`active` | `blocked` | `done` | `stopped`

`blocked` 不是路線。阻塞記在 `manifest.blocks[]`：`id`、受影響的需求／任務、解除條件、進入時間。同一項目重複回報不新增計數。

核准檔只認 hash：

```json
{
  "artifact": "execution-spec",
  "revision": 1,
  "content_hash": "sha256:...",
  "approved_at": "2026-09-26T00:00:00+08:00"
}
```

被核准或被審查引用的 `revisions/rN.md` 之後 hash 變了，檢查直接失敗。現行檔可以改；一引用就先凍結複本再改下一版。

### 3.2 權限邊界

每次 `run start` 與恢復都重算 git 基準，不沿用舊 porcelain。基準變了先標受影響的任務、核准、證據，不自動宣告失效範圍之外的東西也失效。

寫入範圍預設：

- 目標 repo 的 `.sdd-dev/runs/<run_id>/`
- 該次任務聲明的產品碼路徑（進開發之後）
- `repo-local` 安裝時的 `.sdd-dev/tool/`

不在授權內、工具直接拒絕的操作：`git reset --hard`、force push、刪除 write root 以外的檔、正式環境與正式 DB 寫入。拒絕是工具檢查，不是 prompt 隔離。平台做不到這層限制時，`manifest.capability_limits` 記缺口，受影響工作維持 `blocked`。

秘密：日誌與證據寫入前掃常見憑證形狀（金鑰、`Authorization`、`.env` 賦值）。掃得到就改寫成 `[redacted]` 並在問題清單記一筆。掃不到的不假裝已隔離。

### 3.3 選路

政策放 `config/policy.json`，版本寫進每次 run。內容是 r4 的表，不是再發明一套 Tier。

自動選路只填建議與理由。使用者指定的路線、核准點、`no_delegation` 優先。選路不擴大「可以改產品碼」的授權。

| 路線 | 工具必須擋住的事 |
| --- | --- |
| `direct` | 沒有簡短 spec 紀錄、沒有驗收對任務、沒有證據，不能標完成 |
| `selected_advisors` | 沒有實作授權。檢查器看到產品碼 diff 就失敗 |
| `full_pipeline` | 沒有對應 revision 的 spec 核准，不能把 plan 標成可執行；沒有 plan 核准，不能把任務標成 `in_progress` |
| `full_pipeline` + `fast_lane` | 同上。精簡的是篇幅，不是核准、獨立審查、驗證 |
| `plan_only` | plan 核准後狀態改 `stopped`，不開執行任務 |
| `no_delegation` | 審查紀錄的 `independent: true` 一律非法。可標 `pending_human` |
| `no_delegation` + `cross_check` | 不啟動第二個 agent。維持 `pending_human` |

`full_pipeline` 升級不清除未知、驗證能力不足、或未授權。該 `blocked` 繼續 blocked。

獨立審查：同一 run 裡 planner／executor 的對話不算。工具只檢查紀錄是否聲明獨立上下文，以及平台能力矩陣是否支持委派。不支持時不能寫 `independent: true`。

計畫審查自動修訂預設 2 輪（`policy.max_revise_rounds`）。一輪 = 一次修改 + 一次獨立重審。到頂仍有阻塞項就停，不刪需求。

審查報告每條問題要有：位置、依據、嚴重度、建議、解除條件、`blocking: true|false`。`READY` 只表示沒有未解阻塞，不是實作授權。不適用的 D 維度要有理由。安全、資料遺失、必要 migration 缺失、對外介面不相容，不能被其他維度抵銷。

### 3.4 驗證

Workspace profile（`workspaces.json`）記可執行指令、前置條件、已知限制：lint、型別、unit、integration、E2E、build。沒有指令就記 `absent` 與原因。初始化結果可重用；指令或規範變了只更新受影響段。git 狀態不放進這份可重用 profile。

`sdd verify` 做的事：

1. 照 profile 跑指令，stdout／stderr 寫進 `evidence/`，附 exit code、cwd、開始結束時間、`codebase_ref`。
2. 比對該驗收列要求的方法。指令 exit 0 只證明那條指令過了。
3. 瀏覽器、API、人工若沒有證據檔，狀態維持 `not_run`。禁止從「檔案改了」推成 `pass`。

既有失敗：另有一份 baseline 證據（這次 diff 之前、或 profile 裡已記錄的已知失敗）才可標 `preexisting`。沒有 baseline，或因此證不了本次驗收，維持 `blocked`。

證據的 `codebase_ref` 與目前 HEAD／髒狀態不一致，該列標 `stale`，不算通過。

### 3.5 角色輸入

不把整包 run 丟給每個角色。工具依角色組一份輸入清單（路徑 + revision + id），角色可在 write／read 邊界內自己打開原始檔。

| 角色 | 預設路徑 |
| --- | --- |
| scout | 來源 spec、`clarify/state.md`、workspace profile、本次 git 基準 |
| planner | 已核准或現行 Execution Spec、clarify、profile、介面摘錄 |
| plan-reviewer | Execution Spec、Plan、政策裡的 D1–D7、codebase 路徑。不附 planner 對話 |
| executor | 單一任務、對應 spec／plan 段落、驗收 ID、檔案責任、依賴、驗證方法 |
| security-reviewer | 相關需求、diff、資料流、信任邊界 |
| verifier | 驗收列、完成宣稱、diff、`codebase_ref`、證據目錄 |

`models.json` 只放角色到模型 id。流程碼不出現模型名稱字串。空值表示用平台當下的模型。Pilotfish 不在這階段進依賴。

### 3.6 量測

`metrics.json` 跟 run 走，不上傳。缺值寫 `unknown`，不寫 0。

計數定義照 r4：澄清＝一次使用者回覆請求；修訂輪＝審查定義的一輪；阻塞＝項目進入 blocked 的事件；subagent＝實際建立數；核准＝使用者真的核准，與核准請求分開。

`first_pass_success`：該需求 revision 的必要驗收各自第一次就是 `pass`，且沒有 `not_run`／`blocked`。revision 一變，舊指標留著，不覆蓋。`final_pass_success` 看目前證據。兩者都不取代獨立審查。

## 4. 階段

順序是依賴，不是行事曆。P1 完成前不做 P4 的檢查器。每階段的測試用假 repo，放在 `tests/fixtures/`，不碰真實專案。

- AC-P0-4 Given `sdd` 不帶參數，When 執行，Then exit 3 並印 usage。

不做：任何 SDD 流程命令。

### P1 安裝與版控選擇

依賴：P0、D-1。

產出：

- `sdd init --mode repo-local|shared-sibling`
- `install.json`：mode、工具位置、工具 hash、建立時間
- `sdd config tracking track|ignore`
- ignore 模式：寫或提示 `.gitignore` 規則，並跑 `git check-ignore` 與 `git ls-files .sdd-dev`。已追蹤檔只回報，不 `git rm`
- 非 git 目錄：記錄保存位置，`vcs: snapshot`，不宣稱有 git 隔離
- `sdd doctor`：路徑對應、模式與目錄是否一致、秘密檔名是否被放進工具 repo。不要求至少兩個 repo
- `sdd update`：印目前 hash、目標 hash、受影響 repo 與設定；預設不執行，`--apply` 才換工具檔。不刪 `runs/`

驗收：

- AC-P1-1 Given 空的 git repo，When `init --mode repo-local` 且選擇 ignore，Then `.sdd-dev/tool` 與 `config` 存在，`git check-ignore` 命中，`git status` 不出現這些檔。
- AC-P1-2 Given `.sdd-dev/config/install.json` 已被追蹤，When 選擇 ignore，Then doctor 失敗並列出已追蹤路徑，磁碟上的檔還在。
- AC-P1-3 Given 兩個 repo 共用同層工具，When 只在 A 寫入 run，Then B 的 `.sdd-dev` 與工具目錄都沒有 A 的檔。
- AC-P1-4 Given 已安裝，When `sdd update` 不帶 `--apply`，Then 工具檔 hash 不變。

不做：需求、計畫、驗證執行。

### P2 Run 識別、凍結、遮蔽

依賴：P1。

產出：

- `sdd run start --workspace <id> --source <path>`
- `run_id`、來源 hash、`codebase_ref`（branch、HEAD、porcelain hash；非 git 用工作樹內容 hash）
- revision 凍結與 hash 比對
- 寫入前紅線掃描
- `sdd run baseline`：重算 git 狀態，列出與 manifest 基準的差異

驗收：

- AC-P2-1 Given 已核准的 `revisions/r1.md`，When 改該檔一個字元，Then `sdd check` 失敗且不改核准 JSON。
- AC-P2-2 Given run 進行中又有人 commit，When `run baseline`，Then manifest 保留舊基準並列出新 HEAD，已存在證據標 `stale`。
- AC-P2-3 Given 證據內容含 `AKIA` 形狀或 `Authorization: Bearer`，When 寫入 evidence，Then 檔內是 `[redacted]`，原文不在 `runs/`。

不做：自動選路。

### P3 Workspace profile

依賴：P1。可與 P2 平行，P6 之前要合。

產出：`sdd workspace add`、`sdd workspace refresh`。

`workspaces.json` 每筆：

- `id`、`path`、`stack`（自由文字，初始化時寫下，不猜商業名稱）
- `conventions`：指向該 repo 既有的規範檔路徑，不複製全文進工具 repo
- `versioning`：該 repo 的版本規則；沒有就 `none`
- `verify[]`：`id`、`command`、`cwd`、`requires`、`limitation`
- `profile_generated_at`

偵測只認常見指令檔（`package.json` scripts、`pyproject`、`go.mod`、`Cargo.toml`、Makefile target）。認不出就 `absent`，不發明指令。

驗收：

- AC-P3-1 Given 有 `npm test` 的假 repo，When `workspace add`，Then profile 有該指令且沒有把 repo 路徑寫進公開工具檔。
- AC-P3-2 Given profile 已存在且指令沒變，When 再次 `run start`，Then 不重寫 `verify[]`。git 基準仍是新的。
- AC-P3-3 Given 沒有測試指令，When 建立 run，Then 該項是 `absent` 加原因，不能顯示成通過。

### P4 需求查核與 Execution Spec

依賴：P2。

產出模板與 `sdd check --stage spec`：

- `clarify/state.md` 六類：Current State、Target State、Expected Delta、Conflict、Unknown、Assumption。每條有 id、證據路徑、是否阻塞。
- `clarify/decisions.md`：問題、影響、選項、建議、回答、revision。已回答的不刪。
- Execution Spec 章節：來源、澄清、範圍、排除、限制、介面、假設、驗收。驗收在進 plan 前就要有 Given／When／Then。驗證方法欄位先留空，P5 填。
- 追溯表骨架：`R` → `AC` → `T` → evidence。P4 允許 `T` 與 evidence 空著，但不允許沒有 AC 的 R。
- `direct` 用同一 schema，檔可以短。檢查的是欄位在，不是字數。
- `selected_advisors` 只寫諮詢結論，`manifest.implementation_authorized` 維持 false。

驗收：

- AC-P4-1 Given spec 有 R 沒有 AC，When `check --stage spec`，Then 失敗。
- AC-P4-2 Given `full_pipeline` 且 spec 仍是 draft，When 把任務標 `in_progress`，Then 失敗。
- AC-P4-3 Given 使用者只核准 revision 1，When 現行 spec 已是 revision 2，Then 核准不被視為有效。
- AC-P4-4 Given `selected_advisors`，When 產品碼出現在該 run 的變更清單，Then 失敗。

### P5 計畫、審查、選路

依賴：P4、D-2、D-3。

產出：

- `policy.json` 與路線檢查
- Plan 必要段：目標、範圍、限制、`AD-n`、介面、預期修改路徑、任務依賴、每條 AC 的驗證方法
- 任務表：`T`、目的、擁有的路徑、依賴、驗收 ID、commit 邊界、狀態
- 審查報告 schema 與 `READY`／`REVISE`／`BLOCKED`
- `max_revise_rounds`
- Plan 核准檔多一個欄位 `auto_commit: false|true`，預設 `false`。改這個值等於改核准內容，要重新核准
- 路徑重疊檢查：兩任務的路徑集合相交且沒有順序依賴，`check --stage plan` 失敗
- `plan_only` 在 plan 核准後把 run 設成 `stopped`

驗收：

- AC-P5-1 Given 兩個任務都列 `src/a.ts` 且沒有依賴，When `check --stage plan`，Then 失敗。
- AC-P5-2 Given `full_pipeline` 審查有未解的 blocking 安全項，When 請求 plan 核准，Then 失敗。
- AC-P5-3 Given `no_delegation`，When 審查紀錄 `independent: true`，Then 失敗。
- AC-P5-4 Given 已滿兩輪修訂且仍有 blocking，When 再送自動重審，Then 命令拒絕且 spec 範圍沒被改。
- AC-P5-5 Given `fast_lane`，When 缺少 spec 核准或 plan 核准，Then 與非 fast-lane 的 `full_pipeline` 一樣失敗。
- AC-P5-6 Given 核准檔沒有 `auto_commit`，When 讀取，Then 視為 `false`。

不做：派出真的 subagent。這階段只定義紀錄與非法組合。真的委派在 P7，而且平台做不到就維持 `pending_human`。

### P6 開發紀錄與真實驗證

依賴：P3、P5。

產出：

- 問題清單 `problems.md`：`P-n`、影響、處理、理由、結果、是否阻塞下游
- `sdd verify --ac <id>`：跑 profile 裡對上的指令，或接受已存在的證據檔（人工／瀏覽器／API）
- 狀態枚舉只有 `pass` | `fail` | `not_run` | `blocked`。另加屬性 `stale`、`preexisting`，不是第五種通過
- 最終 `report.md`：完成、證據路徑、剩餘、延後。延後必須有理由，預設不延後
- 整合檢查清單：任務各自的檢查、整合檢查、最終驗收分開列
- `sdd commit --task <T-n>`：唯一給 agent 用的 commit 入口。條件：
  - plan 核准有效且 `auto_commit: true`
  - 該任務的必要檢查都是 `pass`，且證據的 `codebase_ref` 對應目前工作樹
  - staged 路徑都在該任務的責任路徑內；執行前已存在的修改不能混進來
  - 只做新 commit。不做 `--amend`、rebase、push
  - 不符合就 exit 1，工作區不動
- `auto_commit: false` 時，report 列出建議的 commit 邊界與訊息，由使用者自己 commit

驗收：

- AC-P6-1 Given profile 有會失敗的 `node -e 'process.exit(1)'`，When verify，Then 該 AC 為 `fail`，證據檔有 exit code，report 不能寫整體完成。
- AC-P6-2 Given AC 的方法是 `manual` 且證據目錄是空的，When 產生 report，Then 狀態是 `not_run`。
- AC-P6-3 Given 指令在 baseline commit 已經失敗且有 baseline 證據，本次 diff 沒碰到該指令涵蓋的路徑，When verify，Then 可標 `preexisting`，且本次必要 AC 仍要另有自己的證據。
- AC-P6-4 Given 沒有 baseline 證據，When 把失敗標成 `preexisting`，Then 檢查失敗。
- AC-P6-5 Given `auto_commit: false`，When `sdd commit --task T-1`，Then exit 1，`git log` 不變。
- AC-P6-6 Given `auto_commit: true` 且 staged 檔有一個不屬於 T-1，When `sdd commit --task T-1`，Then exit 1，`git log` 不變。
- AC-P6-7 Given `auto_commit: true`、T-1 檢查通過、staged 只含 T-1 路徑，When `sdd commit --task T-1`，Then 新增一個 commit，HEAD 的父節點是原 HEAD，遠端不變。

`sdd commit` 只管「經由工具」的 commit。agent 直接跑 `git commit` 要靠平台擋，能不能擋由 P7 的矩陣回答；擋不住就記為缺口，不宣稱已強制。

產品行為對不對，由目標 repo 的指令與證據判定。`sdd` 不重做一套 lint。

### P7 平台矩陣

依賴：P1。與 P4–P6 平行，但「獨立審查」的 `independent: true` 在 P7 之前只能是 `pending_human` 或測試裡的假平台。

先做能力探測，不先做三套完整 hook：

| 能力 | Claude Code | Cursor | Codex |

| 獨立上下文的委派 | 實測後填 | 實測後填 | 實測後填 |
| 唯讀審查 |  |  |  |
| 瀏覽器 |  |  |  |
| 擋破壞性 git |  |  |  |
| 擋直接 `git commit`（D-2） |  |  |  |

探測結果寫進 `docs/platforms.md`（工具文件，不含使用者專案資料）。做不到的格子是缺口，不是「等同 Claude Code」。

舊 Claude Code hook 不搬；舊 `integrations/claude-code/settings.js` 只留「移除時保留他人 hook」這條測試斷言，實作重寫。r4 的強制點是：該路線的核准與驗證不過，就不能把 run 標完成。hook 若存在，只負責呼叫同一個 `sdd check`，並在安裝時備份、解除安裝時只刪自己的條目。

驗收：

- AC-P7-2 Given hook 安裝在假的設定檔，When uninstall，Then 只移除 sdd 條目，其他 hook 還在。

## 7. 風險

- 舊碼只剩 `b00edf7`。這個 commit 目前只在本機，比 `origin/main` 多 2 個 commit。本機 repo 若遺失，舊碼與 proposals 一起消失；要保留就先 push `main`。
- 刪除 commit 必須跟新增分開（P0 commit 切法第 1 步），否則 diff 無法 review。
- D-2 的「不能 commit」只在經由 `sdd commit` 時由工具強制。平台擋不住直接 `git commit` 時是流程約定，不是隔離。
- 獨立審查在單 agent 平台上不可證明。工具只能拒絕假的 `independent: true`，不能製造第二個上下文。
- 自動選路的觸發（影響範圍、可回復性）沒有可靠的靜態判定。v1 讓 scout 填證據清單，人可覆寫；不寫「看檔案數」的啟發式當門檻。
- 憑證掃描會漏。漏了就當缺口，不把「已掃描」寫成「已安全」。

## 8. 實作切法

先做 P0，讓 `npm test` 與 `npm run privacy-check` 在空樹上跑得起來。之後第一個可跑的垂直切片是 P1 + P2 + P4 的 `direct`：假 repo 裡能 init、開 run、寫簡短 spec、檢查「有 AC、核准 hash 沒被改、秘密被遮」。P5 的 `full_pipeline` 在這條切片綠了之後再加。P6 接上真的指令執行。P7 不阻塞 `direct`。

公開工具的 privacy scan 在每次要 commit 工具碼之前跑。掃描對象是工具 repo 自己，不是使用者的 `.sdd-dev/runs/`。
