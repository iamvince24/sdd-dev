# 編號規則與任務分級

只在需要查細節時載入這份文件；日常規則摘要見 `../README.md`。

## 編號規則

追溯就靠這套編號，沒有編號等於沒有追溯。

| 前綴 | 意思 | 寫在哪 |
| --- | --- | --- |
| `R1`、`R2`… | 需求。一句使用者可見的結果 + 一句 why | `00-spec.md` |
| `R1.1`、`R1.2`… | 驗收條件（AC）。必須能客觀判定真假 | `00-spec.md` |
| `NG1`… | Non-goal，明確排除 | `00-spec.md` |
| `Q1`… | Claude 提問 + 使用者回答原文 | `00-spec.md` |
| `DEV-1`… | 規格偏離登記 | `00-spec.md` |
| `D1`… | 技術設計決策，標 `→ R1.1, R2.3` | `01-plan.md` |
| `INV-1`… | 不變量（這次**不能弄壞**什麼），三段式 | `01-plan.md` 第 6 節，驗在 `03-verify.md` 回歸風險表 |
| `T1`… | 任務，標 `→ R1.1` + 檔案 + done 條件 | `02-tasks.md` |

`INV-n` 與 AC 分開編號是刻意的：AC 是「這次要做到什麼」，`INV-n` 是「這次不能弄壞什麼」，
後者用 AC 表達本來就不合身（它沒有對應的需求，但它一旦壞掉代價最大）。
兩者共同點是都必須逐條對帳，不能只留一段散文。

commit message 可選擇性帶編號，例如 `feat(ui): add item list (R2.1)`。

孤兒項目（沒有 AC 的 R、沒有 T 的 AC、沒回指 AC 的 T）不要用眼睛掃過去判斷，
跑 `devplan check --repo <repo-id> --item <release/item> --gate G1`，見 `automation.md`。

## 任務分級

Spec-driven 最常見的失敗是**小事被大流程拖住**。所以先分級，再決定要產哪些檔。

分級**不是判斷題，是勾選題**。以前這裡寫的是散文條件（「單檔、可逆」／「數檔，無新頁面」），
結果每個項目開頭都要重新辯論一次 Tier，而且辯的是使用者最沒有資訊優勢的技術問題。
現在改成封閉觸發清單：Claude 只負責逐條勾選並附證據，使用者只負責確認勾得對不對。

| 觸發 | 在這個 repo 的意思 |
| --- | --- |
| 需求本身還不確定 | `00-spec.md` 還有 `open` 的問題，或 AC 仍有 `[C]` |
| 跨子系統協作 | 同時修改兩個以上具有不同責任、部署或擁有者的子系統；實際路徑規則放在本機 codebase profile |
| 對外／持久化契約 | 新增或修改後端 API 契約、DB schema、localStorage 結構 |
| 信任邊界 | 權限、登入、個資、對外輸入的驗證 |
| 尚未拍板的重大決策 | 有使用者還沒回答、且不同答案會改變作法的問題 |

判定規則：

- 命中 **0** 條 → **S**
- 命中 **1** 條 → **M**
- 命中 **2 條以上**，或命中「信任邊界」 → **L**

**禁止用工作量大小判斷 Tier。**「要改很多檔」不是 L，「只改一個檔但碰權限」才是 L。
工作量會影響排程，不影響這次要不要有獨立審查——後者只看碰到了什麼。

清單一定會有邊緣案例掉在格子外。做法是**補一條進清單**，不是允許一次臨時的例外判斷，
否則就退回散文條件了。

公司或 repository 特有的目錄、模組與子系統名稱不得寫回這份公開文件或檢查器。
需要自動判斷時，寫入 ignored 的 `state/projects/<repo-id>/refs/codebase-profile.json`；
格式與資料隔離規則見 `privacy-boundary.md`。

| Tier | 產出 |
| --- | --- |
| **S** | 只在 `notes.md` 記一行，直接做 |
| **M** | `00-spec.md` + `02-tasks.md`（設計併入 tasks） |
| **L** | 四個檔都要 + 獨立 plan 審查（G2）+ 獨立驗證（G3） |

Tier 判定寫在 `00-spec.md` metadata 表的「Tier」欄，並在 `notes.md` 決策理由表寫一列
記下勾中了哪幾條；`gate-guard.js` 會讀那一欄決定 G2／G3 要不要強制檢查獨立審查紀錄。
