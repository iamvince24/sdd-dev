# sdd-dev 過度設計評估

| 欄位 | 內容 |
| --- | --- |
| 日期 | 2026-09-27；平台支援範圍於 2026-10-06 更新 |
| 評估對象 | 目前工作樹的程式、測試、README 與開發規劃 |
| 評估目的 | 找出維護成本高於現階段實際效益的設計，並提出較簡單的替代方式 |
| 本文性質 | 分析文件；不代表已核准重構，也不授權修改產品程式 |

## 1. 結論

sdd-dev 目前沒有明顯過多的 class hierarchy、DI container 或 factory。程式主要是 CommonJS 函式模組，CLI 分派也沒有複雜 framework。可直接觀察到的成本是：簡單任務仍需多次輸入命令、安裝與平台組合需要維護，以及 Markdown 資料格式和 shell 分類器需要自製解析與測試。

產品同時涵蓋下列責任：

- SDD 工作流引擎
- revision、核准與稽核記錄
- 工具安裝、更新與設定遷移
- 安全操作分類與授權層
- Claude Code 與 Codex 的跨平台 adapter
- 流程事件與指標系統

這些責任是否超出現階段需求，仍要看已確認的產品目標與真實使用情況；不能只因尚無使用資料就認定沒有需求。本文將建議分成三種不同決策：**操作簡化**可先減少重複輸入並沿用現有檢查；**需求刪減**須確認使用情境及相容方案；**資料模型重構**須先處理跨模組契約與既有 run。三者不應視為同一個精簡步驟。

## 2. 評估方法與限制

本次判斷主要使用三個準則：

1. 某項設計是否已有真實使用情境，還是先為未來可能性付出成本。
2. 同一份資料是否有多個真實來源，需要額外的同步與一致性檢查。
3. 複雜度是否直接保護正確性或安全，還是主要處理尚未被驗證的產品情境。

限制：專案內沒有真實使用量、安裝模式分佈、各路線啟用比例或 metrics 的使用記錄。資料不足只表示尚不能判定效益，不表示沒有使用或沒有需求。

原評估記錄曾執行 145 項測試且全數通過；本次文件修訂未重跑測試。該記錄不能證明每個功能都有必要，也不能當成本次工作樹的驗證結果。

## 3. 已觀察到成本、仍需取捨的設計

### 3.1 自製安裝、更新與遷移系統

目前同時支援：

- `repo-local` 與 `shared-sibling`
- 工具檔複製、內容雜湊與版本記錄
- 共用 repo registry
- 安裝模式切換
- 設定 schema migration
- track 與 ignore 模式
- update、doctor 與 uninstall

相關邏輯分散在 [`lib/install.js`](../lib/install.js)、[`lib/registry.js`](../lib/registry.js)、[`lib/tool.js`](../lib/tool.js)、[`lib/tracking.js`](../lib/tracking.js)、[`lib/migrations.js`](../lib/migrations.js) 與多個 command 模組。這是已存在的維護面；但[開發計劃](開發計劃.md)已具體規劃兩種安裝模式、各 repo 的設定與 run 邊界，以及更新與搬移檢查。`private`、版本 `0.0.0`、README 的 checkout 用法或程式行數，都不足以推翻這項需求。

#### 建議與決策條件

- 先指定一種主要安裝模式，集中說明與實測，暫停擴充另一模式的新能力；保留既有使用者可用的路徑。
- 若要移除安裝模式、registry 或 mode switch，先確認兩種模式的使用情境、既有安裝與 run 的相容及遷移方案，並更新已確認的產品需求。
- npm package 或 tarball 可處理工具發佈與版本更新，不能代替 `.sdd-dev/config/`、`.sdd-dev/runs/` 的相容、搬移與遷移規則。

### 3.2 `direct` 路線仍然很像完整稽核流程

最簡單的 `direct` 任務，README 列出的操作仍包含：

1. 寫 Spec。
2. 檢查 Spec。
3. 寫 Plan。
4. 執行 verify。
5. 寫 evidence。
6. 標記 done。

每個 run 又可能產生 manifest、sources、clarify、spec revisions、impact、plan revisions、review、approvals、contexts、problems、evidence、metrics 與 report。對局部、可回復的小修改，這些檔案的閱讀與維護成本可能高於收益；目前仍缺少實際操作時間與檔案使用資料來量化。

#### 先簡化操作，再評估資料模型

- 優先提供 `sdd run quick` 一類入口，一次收集簡短 Spec、Plan 與驗收對應，再沿用現有檢查、驗證、證據與完成流程，減少手動輸入。這是操作簡化，不要求先改資料模型。
- 將 `direct` 改成單一 `run.json` 或 `run.md` 是另一項重構。目前 [`lib/route.js`](../lib/route.js) 從 Spec、Plan 判斷授權及寫入範圍，[`lib/verify.js`](../lib/verify.js) 也直接讀兩份文件；真正改成單一資料來源時，這些讀取與檢查都須調整，不能只合併輸出檔。
- 不因路線是 `direct` 就刪除 revision、使用者指定的核准、需求到證據的對應或證據過期判定。[需求規劃](SDD規劃.md)允許 `direct` 使用簡短紀錄，仍要求 Execution Spec、Plan 的 revision 與必要追溯。獨立審查及核准依風險與使用者要求決定。
- 將 `selected_advisors` 改為不建立完整 run 的唯讀諮詢命令僅是候選方案；先確認恢復諮詢、保存結論與不得自行實作等需求如何維持。

### 3.3 用 Markdown 當機器狀態格式，再自製解析器

Spec 目前同時使用：

- 自製 frontmatter parser
- HTML section marker
- 自製縮排條目 parser
- current file 與 frozen revision 的逐位元組同步

相關邏輯可見 [`lib/spec.js`](../lib/spec.js)。Review 又另外解析巢狀 frontmatter、finding 欄位與布林字串，可見 [`lib/review.js`](../lib/review.js)。

這個選擇讓「給人閱讀的文件」同時負責正式資料格式、revision 儲存、diff 單位、關聯資料與狀態驗證。新增多行欄位、特殊字元或巢狀資料時，都需要擴充自製格式。

#### 候選方案與前提

- JSON canonical data 與 JSON Schema 是候選方案；先定義使用者如何編輯、審閱與核准，以及 Markdown 閱讀版如何產生、保存及對應正式資料。若沿用 YAML，也須評估成熟 parser 的依賴與維護成本。
- 先列出 Spec、Plan、Review、授權、驗證、報告與角色上下文的資料讀寫契約。這些模組目前依賴 Markdown 欄位或檔案位置；更換格式須同步調整，並讓既有 run 可讀或有不丟資料的遷移路徑。
- 可評估以不可變 revision 為唯一內容來源、current 只保存指標，但須定義 hash 的計算對象、核准引用方式、來源變更後核准與證據如何失效，以及中途寫入失敗時的恢復語意。未定義前，不宜把移除 current 與 frozen 複本視為已確認的簡化。

### 3.4 自製 shell 安全政策解析器

[`lib/guard.js`](../lib/guard.js) 約用 360 行自行處理：

- quotes、pipe、分號、`&&` 與 `||`
- `bash -c` 與 `sh -c`
- Git 全域參數、force push、rebase 與 reset
- `rm`、glob 與 realpath
- npm、pip、cargo 與 go 安裝
- curl、wget、ssh 與 scp
- SDD 使用者專屬指令

Shell grammar 很難靠 token parser 完整處理。現有邏輯可以擋下常見指令，但不能當成完整安全邊界。Redirection、其他 shell、alias、間接執行、其他網路工具與腳本內部行為，都可能超出分類器能理解的範圍。

[`docs/platforms.md`](platforms.md) 記錄了當時的特定探測：多數能力未測，且該次 Codex sandbox 測試未擋住列出的 force push、workspace 外刪除與連網情境。這些結果是探測當時的證據，不能直接推論所有版本、設定或平台都相同。

#### 替代方式

- 平台能提供結構化工具呼叫時，先判斷工具名稱與參數；若參數仍是 `sh -c` 或其他 shell 指令文字，仍須依 shell 語意處理，不能視為已避開解析問題。
- 寫入範圍交給 OS sandbox 或平台原生權限層。
- 不支援強制點的平台，明確標示 capability gap，不宣稱已能防止。
- `sdd` 自己執行的操作仍保留嚴格驗證，例如 `sdd commit` 與 `sdd update`。
- 若 hook 只能收到 shell 字串，改用保守 allowlist 或要求人工確認，不把 parser 當成完整安全機制。

這一塊不應直接刪除，而是縮小它宣稱能保護的範圍。

## 4. 需要使用資料才能確定的部分

### 4.1 平台、路線、修飾詞與能力矩陣的組合

目前同時有：

- 2 個平台
- 3 條 route
- 4 個 modifier
- 9 個 capability cell
- 各平台專屬 instruction 安裝與還原

相關實作可見 [`lib/capabilities.js`](../lib/capabilities.js) 與 [`lib/instructions.js`](../lib/instructions.js)。目前 [`integrations/capabilities.json`](../integrations/capabilities.json) 只有 Codex 三格有值，Claude Code 沒有已填的實測資料。2026-09-27 的原評估曾記錄 Cursor 兩格；Cursor 已停止支援，該紀錄不屬於目前能力矩陣。矩陣的九項能力分別對應委派、審查、瀏覽器及各種強制點；未測的 `unknown` 與實測失敗的 `false` 必須維持區別。能力不足會記入限制，只有列在政策 `required_enforcement` 的項目才因缺少強制點而阻塞 run，不能將「未測」概括為所有工作都已被阻塞。

2026-10-06 維護補記：Cursor 專屬 adapter 與規則產生流程已移除，只留下舊安裝偵測與歷史 run 的拒絕處理。這些保護不提供 Cursor 支援，也不自動遷移或刪除資料；清理流程見 [Cursor 支援移除與舊資料處理](cursor-retirement.md)。本次縮小平台範圍沒有刪除 route、modifier 或能力欄位，也沒有變更未量測與實測失敗的判定。

推論：目前的測試成本可能隨平台與路線組合增加，但不能單憑矩陣未填滿就刪除能力項目或改變持久化政策。[需求規劃](SDD規劃.md)已要求跨工具能力邊界與使用者選路，調整前須確認需求。

#### 建議

- 先選主要平台，集中實測九項能力及實際路線；其他平台清楚標示已測、未測與已知失敗的範圍。
- 保留必要能力矩陣及 `unknown`／`false` 語意。依政策判斷哪些強制點必須具備，其餘限制如實呈現，不用未測資料推斷支援或不支援。
- 若要刪除低使用率 modifier、能力欄位或 run 中的紀錄，先取得使用與恢復 run 的資料，再決定相容方式。

### 4.2 事件與 metrics 的保存成本

[`lib/metrics.js`](../lib/metrics.js) 已計算路線升級、風險、澄清、阻塞、subagent、核准、等待時間、首次通過、覆寫與後續返工等資料。[需求規劃](SDD規劃.md)明定要記錄流程成本、驗證與後續結果，這些指標有需求依據；目前缺的是實際使用與決策紀錄，不能據此斷定整組過早或無用。

[`lib/events.js`](../lib/events.js) 每次新增事件都會讀取整份 JSONL 以找出最大 ID，隨事件數增加，累積掃描量可能接近 O(n²)。這是可由程式推得的成本，尚無量測能證明它是目前的效能瓶頸。改用 manifest counter 會引入跨檔一致性問題，UUID 也會改變識別方式，需先確認實際瓶頸與需求。

#### 建議與資料保存條件

- 先確認哪些指標有被查看、用於何種流程決策，再限制新增欄位或事件種類。
- 不直接刪除 `metrics.json`：`first_pass_success` 按需求 revision 保留首次結果，`outcomes` 保存後續返工等觀察，現有其他資料未必能重算。若改為查詢時計算，須先搬遷這些原始事實並驗證既有 run 的結果一致。
- 保留計算執行與等待時間所需的 `status`、`pending_human` 事件及時間資訊。只有確認其他資料來源足以還原語意後，才評估精簡事件。
- 若量測證實事件 ID 掃描造成問題，再比較現行方式、counter 與 UUID 的成本及恢復語意。

## 5. 不建議當成過度設計的部分

### 5.1 CLI 分派與 command 模組

`bin/sdd.js` 與 `lib/commands/` 之間是薄的參數分派層，沒有 command framework、factory 或依賴注入架構。命令數量多是產品範圍的結果，不是這層程式分層造成的。

### 5.2 實作授權與寫入範圍重算

`implementation_authorized` 與 `write_roots` 是安全狀態的一致性邊界。不應為了減少模組數，改成由各個 command 自行設定或讓使用者手動修改 manifest。

### 5.3 baseline dirty hash 與過期證據檢查

這些邏輯直接避免把 run 開始前就存在的修改，或與目前程式狀態不同的證據，當成本次完成結果。這是可驗證正確性的功能，有清楚用途。

### 5.4 零第三方 runtime dependency

對可攜式 CLI 而言，減少 runtime dependency 有合理的供應鏈與安裝考量。但這不應引導專案重新實作 YAML parser 或 shell parser 等高風險格式。

## 6. 建議的精簡順序

1. 先簡化 `direct` 操作入口，減少重複輸入，沿用現有 Spec、Plan、授權、驗證與證據檢查。
2. 明確界定 shell guard 的保護範圍，集中實測主要平台的必要強制點，依結果標示能力限制。
3. 收集安裝模式、路線使用量、操作時間、驗收與返工資料，再決定是否刪減安裝模式、平台組合或其他產品需求；刪減前先備妥既有使用者的相容方案。
4. 最後再評估 `direct` 單一 artifact、JSON canonical data 與 metrics 儲存方式。這些會改變跨模組資料契約、既有 run 的讀取或遷移，以及核准和證據的失效語意。

第 1 步是可先評估的操作改善，不代表已核准刪除 revision、核准或驗證。其餘步驟各有需求確認與相容條件，不應以「精簡」一詞跳過。

## 7. 候選責任邊界

若後續要整理模組責任，可用下表討論；這不是已決定的新資料格式或功能刪減清單。

| 層次 | 責任 | 保留條件與待定事項 |
| --- | --- | --- |
| Core run | 建立需求基準、任務、範圍與驗收對應 | 各路線保留必要 revision、追溯及授權邊界；資料格式待定 |
| Verification | 執行驗證、記錄結果與 codebase reference | 保留必要證據、baseline 與 stale 判定 |
| 路線專屬控制 | 依路線及使用者要求執行核准、審查與影響評估 | 完整流程有強制條件；其他路線仍可能需要 revision、核准或審查 |
| Platform adapter | 產生平台指令並回報已實測能力 | 集中實測主要平台，保留必要能力與未知狀態 |

安裝與更新的實作責任可另行整理，但工具發佈不能取代設定、run 與跨 repo 相容處理。部分 metrics 可由其他資料計算；首次結果與後續 outcome 等原始事實須先確認保存位置，才能決定是否取消每個 run 的 `metrics.json`。

## 8. 後續決策前需要的資料

若要決定哪些功能正式移除，先收集：

- `repo-local` 與 `shared-sibling` 的實際使用次數
- `direct`、`selected_advisors` 與 `full_pipeline` 的啟用比例
- `direct` 改善前後的命令數、手動輸入量、完成時間與錯誤次數
- 哪些產出檔實際被人開啟或在恢復 run 時讀取
- 首次驗收、最終驗收、後續返工與等待時間如何被使用
- 各平台真實能力的探測結果

尚無使用量資料不等於沒有使用。資料不足時，先凍結新增組合並簡化入口，再用真實任務及可重跑案例比較。至少確認：`direct` 的手動操作量確實下降；原有授權、寫入範圍、必要驗證、證據過期與獨立審查條件仍成立；既有 run 可讀，或遷移後不遺失核准、首次驗收及 outcome 等紀錄。達到這些條件後，再決定是否刪除產品路徑或改資料格式。
