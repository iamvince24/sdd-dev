## 逐條 AC 結果

狀態用 `PENDING` / `PASS` / `NOT-PROVEN` / `FAIL` / `BLOCKED` / `N/A（偏離 DEV-n）`。

最容易被含混掉的是 `PASS` 與 `NOT-PROVEN` 的差別。少了 `NOT-PROVEN`，
「有驗、但證據不足以證明」只能硬塞進 `PASS`（說謊）或 `BLOCKED`（不精確 ——
`BLOCKED` 是「驗不了」，不是「驗了但不算數」）：

| 狀態 | 什麼時候用 |
| --- | --- |
| `PASS` | 驗了、通過，**證據離開這個 session 還能重現** |
| `NOT-PROVEN` | 驗了、看起來對，但證據無法離線重現（只有「畫面正常」這類敘述） |
| `BLOCKED` | 沒辦法驗（缺測試環境、缺後端資料、依賴他人尚未交付） |
| `FAIL` | 驗了、不通過 |

**`NOT-PROVEN` 不得進 `done/`。** 歸檔前每一條都要轉成 `PASS`（補到可重現的證據）、
`FAIL`、`BLOCKED`，或登記成 `00-spec.md` 的 `DEV-n` 偏離。它的用途是把「懶得補證據」
從隱形變成可見，不是一個可以永久停留的狀態。

**「證據」欄必須是離開這個 session 之後還能重現的東西**，否則等於沒有證據：

| 可以 | 不可以 |
| --- | --- |
| 貼上 Network 回應的關鍵片段（`"sort": 12`） | 「目視確認 OK」 |
| 截圖存成 `refs/evidence/R4.1-edit-sort.png`，欄位填路徑 | 「畫面正確」 |
| 貼上實際跑的指令與輸出摘要 | 「測過了沒問題」 |
| 指到 commit hash 或 `file:line` | 「跟計劃一致」 |

截圖與匯出檔一律放 `refs/evidence/`，檔名以 AC 編號開頭。

**填完之後跑一次自動檢查，不要只憑感覺判斷證據合不合格：**

```bash
devplan check --repo <repo-id> --item <release/item> --gate G3
```

它會挑出「目視確認 OK」這類無法重現的敘述，以及狀態非空但證據欄是空的列；
證據看不出任何可重現型態的列會被**直接判為 `NOT-PROVEN`**。
被挑出來的列在回報完成前要先補證據或改判狀態。

**「驗證時 spec 指紋」欄**填驗證當下 `00-spec.md` 的語意指紋，用
`devplan fingerprint --repo <repo-id> --item <release/item>` 取得。
`00-spec.md` 之後改了需求，指紋就對不上，這一列會被判為 `STALE`（要重驗）——
這是失效鏈裡「`00-spec.md` 升版 → `03-verify.md` 已填的所有列失效」那一條的機器版本。
沒有這一欄的話，spec 改過之後這些列在機器眼中完全正常。
