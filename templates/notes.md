## Gate 狀態

**核准綁內容，不是綁人手寫的版本號** —— 核准的是「當下那份內容」。核准時把
`devplan fingerprint --repo <repo-id> --item <release/item>` 印出的**語意指紋**填進「核准指紋」欄；
之後文件的實質內容一改，指紋就對不上，該 Gate 自動失效。
版本號欄保留給人讀，機器判定看的是指紋 —— 改了 AC 卻忘記升版時，版本號比對會安靜地通過。

指紋刻意只涵蓋「改了就該重新核准」的部分：任務的**狀態欄**、`notes.md`、補證據、
純粹的換行重排都**不會**改變指紋，所以收尾白名單多數情況自動成立。
唯一涵蓋不到的是 AC 本文的錯字——那仍然要在修訂紀錄註明「不影響核准」來豁免。
細節見共用工具的 `docs/decision-anchors.md`。

**「狀態」欄核准後要填「已核准」**（後面可以再加日期或說明）。`gate-guard.js` 會掃這個字樣：
空白、「待核准」、或任何沒有這個標記的散文，一律判為尚未核准並回報 blocker。
這是為了讓「人還沒核准」在機器層面看得見 —— 否則一個項目可以整份 vTBD、狀態欄空白，
卻拿到「機器可驗證的部分都通過」。

**不要只靠這張表的人工記錄判斷 Gate 還有沒有效**——跑
`devplan check --repo <repo-id> --item <release/item> --gate <G1|G2|G3>`，它會直接比對這裡填的核准版本
與文件目前的實際版本，版本兜不起來就會回報「Gate 已過期」。

| Gate | 狀態 | 核准的版本 | 核准指紋 | 日期 |
| --- | --- | --- | --- | --- |
| G1 Spec 核准 | | `00-spec.md` vTBD | | |
| G2 Plan + Tasks 核准 | | `01-plan.md` vTBD + `02-tasks.md` vTBD | | |
| G3 Spec ↔ 實作驗證 | | `00-spec.md` vTBD | | |

## 獨立審查紀錄（plan-verifier / verifier / security-reviewer）

**只寫「審為 READY」是不夠的。** 審查過程中提出的 blocker、以及我把它判成
`FIX`／`DEFER`／`REJECT` 的理由，如果不落檔就只存在於那一次對話 ——
下個 session 改計劃時很可能重犯已經被指出過的問題。每一次 Agent 審查都要有一列。

Tier L 專案的 G2／G3，`gate-guard.js` 會檢查這張表**是否存在對應 Gate 的完整列**
（Verdict、blocker、處置與理由都非空白）——沒有就代表獨立審查沒有真的落地，
即使核准版本比對通過，腳本也會擋下。

兩欄要特別說明：

- **三軸（O／M／C）** —— 格式 `O:PASS M:PASS C:PASS`。
  `Outcome`（行為對不對得上 AC）／`Minimality`（有沒有多做沒被要求的東西）／
  `Conformance`（有沒有違反 `refs/codebase-gotchas.md` 的既有義務）。
  **三個都 PASS 才能在 `Verdict` 欄寫 PASS。** 只看 Outcome 的話，「多做」與
  「違反既有慣例」這兩種問題可以完全合格地通過覆蓋率對帳。
- **回指** —— 填對應的 AC 編號、或 `follow-up`、或 `reject`。
  **處置是 `FIX` 而回指欄空白 = 範圍擴張，不允許。**
  park 成 `follow-up` 的落點是 `03-verify.md` 的「未通過與 Follow-up」節（小事）
  或另開一個 `active/` 項目（大事），不要留在這裡自生自滅。

### 給 subagent 的範圍紀律（brief 裡逐字帶上）

> 你提出的發現不會自動成為工作。要主張某個行為必須被修正，先指出它對應
> `00-spec.md` 的哪一條 AC、或 `refs/codebase-gotchas.md` 的哪一條既有義務。
> 指不出來的，標成 `follow-up` 提案，不要寫成 blocker。
> 嚴重度與假設性的失敗路徑是證據，不是擴張範圍的授權。
>
> 回覆請分別給 `Outcome`／`Minimality`／`Conformance` 三個判定，再給一個總 `Verdict`；
> 三個都 PASS 才算總 PASS。
